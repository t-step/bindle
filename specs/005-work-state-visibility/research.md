# Phase 0 Research: Work-State Visibility

**Scope note (post-implementation reconciliation)**: the decisions below cover both the adopted scope (User Stories 1–4: `bindle work status`, `bindle work forecast`, `is_dispatchable()`) and a fifth surface, `bindle view`, that was planned alongside them but evaluated after US1–US4 existed and declined — see `docs/DECISIONS.md` D045. Every decision below whose title names `bindle view` or Symphony runtime enrichment is retained as historical research only, clearly labeled **(NOT ADOPTED — declined, see D045)**; it documents real design work performed during planning, not implemented or pending behavior. Every other decision below (dispatchable sourcing, milestone readiness sourcing, forecast relation, `is_dispatchable()` sharing, dangling blocking ids, `not_ready_reason` rendering, no-timestamp JSON contract, `--watch` interval/framing, watch shutdown behavior) describes the adopted, implemented feature.

## Decision: one `WorkStatusSnapshot`, built once, consumed by every renderer

**Chosen**: A single function, `work_status.build_snapshot(ledger: WorkLedger) -> WorkStatusSnapshot`, is the only place any of this feature's code reads task/milestone claim, blocking, status, or review-readiness facts from the ledger. `bindle work status`'s plain-text and `--json` forms both format the identical `WorkStatusSnapshot` object; `bindle work forecast`'s `DependencyFrontier` is derived *from* that same object (next decision); `bindle view` builds one `WorkStatusSnapshot` (+ one derived `DependencyFrontier`) per HTTP request and renders both.

**Rationale**: spec.md's own framing states this directly — "`bindle view`'s own read model is this JSON shape, not a second, independently-derived computation" (User Story 2's "Why this priority") — and the planning brief's expected shape (`canonical ledger → semantic read model → {status text, JSON, forecast} → view`) names exactly one composition layer feeding every presentation. Building the snapshot once per invocation/request and deriving forecast from it in memory is also what makes "no cross-query locking, a snapshot may be stale by the time it is displayed" (spec.md Edge Cases) an accurate description of this feature's actual behavior: within one `build_snapshot()` call, every fact is fetched close together in wall-clock time, but still through the ledger's own existing connection-per-call reads — no new transactional guarantee is introduced, and none is needed (spec.md explicitly accepts staleness as expected, not a defect).

**Alternatives considered**: Three independent composers (one per command) each calling `WorkLedger` directly — rejected outright; this is exactly the "nothing today aggregates task and milestone state together" gap the spec identifies, and three independent composers would risk exactly the drift FR-002/FR-003/FR-004 forbid (a future edit to one command's derivation silently disagreeing with another's).

## Decision: `dispatchable` (present state) is sourced from `list_available_work_items()` verbatim, never re-derived

**Chosen**: `build_snapshot()` calls `ledger.list_available_work_items()` once and uses the returned id set as the sole source of truth for which tasks are dispatchable *right now*. It does **not** compute `dispatchable = status == 'open' and not claimed and not blocked` itself from the per-item facts it separately fetches for other purposes, even though that boolean expression is mathematically identical to the query `list_available_work_items()` runs.

**Rationale**: Terminology's own wording is emphatic — "This feature never recomputes this predicate independently" — and FR-002 requires "the identical existing predicate ... already compute[s]," not merely an equivalent one. Calling the existing method directly means a future change to `list_available_work_items()`'s own guard conditions (e.g., a new precondition added to `specs/001`'s dispatchability rule by some later feature) is inherited automatically by `bindle work status`/`forecast`/`view` with zero code change here, and can never silently drift from a hand-rederived boolean that happened to be correct only as of this feature's own implementation date.

**Alternatives considered**: Deriving the boolean per-item from `status`/`get_claim()`/`list_blocking()` (values `build_snapshot()` fetches anyway) — rejected for the drift risk above, even though it would save exactly one additional ledger call per invocation; at this repository's stated scale (a handful-to-dozens of work items, per 001–004's own precedent) that call's cost is immaterial.

**Scope of this decision**: this covers `dispatchable_now` only — the present-state fact `list_available_work_items()` can actually answer, since it only ever queries live ledger state. It says nothing about `dispatchable_next` (the forecast counterfactual "would this become dispatchable if blocker X resolved"), which `list_available_work_items()` structurally cannot answer at all — see the next-but-one decision, "dispatchable-next shares one authoritative predicate," for how that counterfactual avoids becoming a second, independent re-derivation of this same rule.

## Decision: milestone readiness/reason is sourced from `milestone_review.review_milestone()` verbatim, once per milestone

**Chosen**: For every `type == 'milestone'` item, `build_snapshot()` calls `milestone_review.review_milestone(ledger, id)` and takes `review_ready`, `not_ready_reason`, `blocking_ids`, and `claim` directly from the returned `MilestoneReviewView` — never `is_review_ready()` called standalone, and never a hand-assembled reason list.

**Rationale**: FR-004 states this explicitly — "the same outstanding-reason detail `milestone_review.review_milestone()` already computes (blocked / no children / which specific child(ren)) — never a new readiness predicate." `review_milestone()` already composes exactly this diagnostic (`research.md`'s own prior decision in specs/004, "readiness diagnostic is composed from existing reads"); re-deriving it a second time in `work_status.py` would be precisely the kind of duplicated lifecycle predicate the planning brief's lifecycle-audit dimension (below) exists to catch.

**Cost accepted, and why it's fine**: `review_milestone()` also computes each child task's full evidence list and per-child blocking state (`MilestoneReviewView.children`) — more detail than the top-level status snapshot renders. `build_snapshot()` discards `children` and keeps only the five fields it needs (id, title, status, review_ready, not_ready_reason, blocking_ids, claim) into a narrower `MilestoneStatusEntry` (data-model.md). This is the same per-row overhead `list_milestones()` already accepts today (`specs/004`'s own "no dedicated batch query" decision) — one extra bounded read per milestone, at a scale where that cost is immaterial, in exchange for zero risk of a second, drifting readiness computation.

**Alternatives considered**: Calling `is_review_ready()` directly (cheaper — a single boolean per milestone) and separately re-deriving `not_ready_reason` from `is_blocked()`/`list_work_items()`/`has_qualifying_evidence()` the way `review_milestone()` itself does internally — rejected: this would be a second, hand-copied implementation of exactly the diagnostic `review_milestone()` already owns, the literal "false equivalence"/"duplicated lifecycle predicate" failure mode the planning brief's dogfooded audit dimension calls out by name.

## Decision: forecast is a pure relate over snapshot facts, not a new predicate

**Chosen**: `work_status.build_forecast(snapshot: WorkStatusSnapshot) -> DependencyFrontier` takes an already-built snapshot and computes, entirely in memory:

- `dispatchable_now` — `snapshot`'s own task-dispatchable id list, unchanged, passed through.
- `convergence_points` — every item (task or milestone) whose `blocking_ids` has more than one entry, i.e. `len(item.blocking_ids) > 1` — a `list.filter` over already-fetched data, not a new SQL predicate.
- `frontier: list[ForecastEntry]` — for every distinct id `B` that appears in *any* item's `blocking_ids` (this includes a dangling/nonexistent id exactly as declared — see next decision): `unblocked_next` is every item whose `blocking_ids == [B]` (losing `B` leaves zero remaining blockers, which is exactly the "every other current ledger fact ... held unchanged" counterfactual Terminology defines), and, of those, `dispatchable_next` is the subset that are tasks for which `work_ledger.is_dispatchable(status=item.status, claimed=item.claim is not None, blocked=False)` returns `True` — i.e., would satisfy the existing, single, authoritative dispatchable predicate the moment `B` resolved (`blocked=False` is the one input this counterfactual supplies itself, since "B was the only blocker and it resolved" is exactly what `unblocked_next` membership already established; `status`/`claimed` are read unchanged from the snapshot, never assumed). See the next decision for why this calls a shared function rather than re-deriving the two-conjunct check by hand.

No ledger query is issued by `build_forecast()` at all; every value above is read from fields `build_snapshot()` already populated, plus one pure, I/O-free function call per candidate.

**Rationale**: spec.md FR-012c/FR-015 require exactly this: a relation "computed entirely from existing per-item blocking, status, and claim facts... introducing no new blocking or dispatchable predicate," and explicitly forbid creating, mutating, or simulating any ledger row to answer "what if X resolved." Grouping by the literal blocking-id string already present in `blocking_ids` — rather than looking up whether that id even resolves to a real, live work item — is what naturally reproduces Terminology's own single-changed-fact counterfactual: "every other current ledger fact ... held unchanged," including every *other* declared `blocked_by` edge on the affected item. Verified by hand against spec.md's own worked example (User Story 4's Independent Test: C blocked on {A, B}, D blocked on {A}) — `frontier['A'].unblocked_next == ['D']` (C is excluded because C's `blocking_ids` is `{A, B}`, not `{A}` alone), `frontier['A'].dispatchable_next == ['D']` iff `is_dispatchable('open', claimed=False, blocked=False)` is `True` for D, and `convergence_points == ['C']`. Also verified against Acceptance Scenario US4.5 (a claimed task blocked by exactly one dependency): that task lands in `unblocked_next` for its one blocker but never in `dispatchable_next`, because `is_dispatchable(status, claimed=True, blocked=False)` is `False` — exactly the "loses a blocker, but remains claimed" distinction the scenario requires.

## Decision: dispatchable-next shares one authoritative predicate with `list_available_work_items()`, not a hand-copied re-derivation

**This is the most consequential correction from this review pass.** The prior version of this plan had `build_forecast()` inline-checking `item.status == 'open' and item.claim is None` for `dispatchable_next` — mathematically correct today, but a second, independent Python expression of two-thirds of the exact rule `list_available_work_items()`'s SQL also expresses, with nothing tying the two together beyond both currently being correct. If a future change ever added a fourth condition to task eligibility (or changed what "open" means), `list_available_work_items()`'s SQL would be updated and this feature's own hand-copied Python check would not automatically follow — a real, if narrow, drift risk, exactly what this review's item 3 was checking for.

**Re-grounded against the actual current implementation this session**: `WorkLedger.list_available_work_items()` (`src/bindle/work_ledger.py`) is a single inline SQL statement — `SELECT id FROM work_items wi WHERE wi.status = 'open' AND wi.type = 'task' AND NOT EXISTS (... work_item_claims ...) AND NOT EXISTS (... work_item_blocked_by ... _STILL_BLOCKING_CONDITION ...)`. There is no separate, reusable Python-level predicate function anywhere in the codebase today — the three-conjunct rule (`type='task'` scoping aside, since that is caller-context, not part of the per-item eligibility check) exists in exactly one place, as SQL, evaluable only against real, live ledger rows. It cannot answer a counterfactual ("if blocker X resolved") at all — there is structurally no way to ask it a hypothetical question without mutating a scratch copy of the ledger, which spec.md FR-015 explicitly forbids. Some new, pure expression of the rule is therefore unavoidable for `dispatchable_next` to exist at all; the question this review correctly poses is how to add it without letting it become a second, independently-maintained copy.

**Chosen**: Add one small, pure, stateless function to `work_ledger.py`, colocated with the existing `_STILL_BLOCKING_CONDITION` SQL fragment (the same file's own precedent for "the canonical expression of one derived rule, factored out for reuse"):

```python
def is_dispatchable(status: str, claimed: bool, blocked: bool) -> bool:
    """The exact task-dispatchability rule list_available_work_items()'s
    own SQL encodes (status == 'open' AND NOT claimed AND NOT blocked),
    factored out as a pure, I/O-free function so it can be evaluated
    identically against live ledger state and against a read-only
    forecast counterfactual (specs/005). Takes no `type` argument because
    every caller already scopes to type == 'task' before calling this —
    the same structural precondition list_available_work_items()'s own
    query already applies before this predicate's three conjuncts."""
    return status == "open" and not claimed and not blocked
```

`list_available_work_items()`'s own internal implementation is refactored so its per-row inclusion decision routes through this same function, rather than re-expressing the identical three-conjunct rule a second time in a SQL `WHERE` clause: it fetches candidate `type = 'task'` rows together with their claimed/blocked booleans — already computed today as `NOT EXISTS` subqueries, exposed as selected row-level values instead of inline filter conditions — then applies `is_dispatchable()` per row in Python to decide inclusion. This is the same "fetch broadly, relate in Python" style `review_milestone()` already uses for its own per-child checks, at the same "handful-to-dozens of work items" scale where the cost is immaterial. Its external behavior, return value, and ordering are unchanged — verified by its own existing, unmodified test suite.

**Why this satisfies "one authoritative definition... including when the same rule is evaluated against a read-only counterfactual snapshot"**: after this refactor, there is exactly one place in the entire codebase where "is this task's status/claim/blocking combination dispatchable" is decided in Python — `is_dispatchable()` — and both the live-state path (`list_available_work_items()`, routed through it) and the counterfactual path (`build_forecast()`) call that same function. The only thing that ever differs between the two callers is *where each of the three inputs comes from* (a live query vs. an already-fetched snapshot value vs. a counterfactual assumption) — never the rule itself. This is genuine shared code, not two independently-maintained expressions of the same rule kept in sync by a test.

**Why this is a bounded, narrowly-scoped exception, not a precedent for touching specs/001–004 generally**: this does modify `list_available_work_items()`'s own query strategy, which is more than this feature's general "read existing methods verbatim, never modify them" posture calls for elsewhere. It is justified only because it is the sole way for `dispatchable_next` to share actual code — not just an independently-tested equivalent expression — with the live predicate, and it is scoped as tightly as that justification allows: the function's external behavior, return value, and row ordering are unchanged and re-verified by its own existing, unmodified test suite; no other query (including `generate_external_projection()`, which expresses the identical rule inline for its own external Symphony-contract purposes and is out of scope for this feature) is touched. `tests/test_work_status.py`'s coherence test (Technical Context, Testing) remains as a regression guard on this refactor, not as the mechanism that establishes the invariant — the invariant is established structurally, by both paths calling the same function.

**What this explicitly is not**: not a generic policy engine, not a graph abstraction, not a scheduler abstraction, not an alternate availability lifecycle — one three-argument, pure, synchronous boolean function with no state, no I/O, and no configurability. `type == 'task'` scoping remains the caller's structural responsibility (as it already is today), not a fourth parameter this function invents authority over.

## Decision: a dangling blocking id is a valid forecast grouping key, exactly as declared

**Chosen**: `build_forecast()` never checks whether a blocking id in `blocking_ids` resolves to an actual work item before using it as a `frontier` grouping key. A dangling reference groups and reports identically to a real one.

**Rationale**: spec.md's Edge Cases state this precisely for the status/forecast facts generally: "It is reported exactly as `list_blocking()` already reports it — conservatively still-blocking — with no special interpretation invented for this feature." `list_blocking()` (which `build_snapshot()` calls verbatim, per the "dispatchable is sourced verbatim" decision above's sibling case) already includes a dangling id unresolved, by design (`work_ledger.py`'s own docstring: "included exactly as declared, unresolved"). Treating it identically in the forecast relation — rather than filtering it out, or special-casing it as "irresolvable" — costs nothing extra and avoids inventing a third interpretation of "blocking" this feature's Terminology never defines.

## Decision: plain-text `not_ready_reason` rendering reuses `cli.py`'s existing `_format_not_ready_reason()` helper

**Chosen**: `bindle work status`'s plain-text renderer for a `MilestoneStatusEntry` with `review_ready is False` calls the existing, private `cli._format_not_ready_reason(reasons, blocking_ids)` (added by `specs/004`, currently used only by `_cmd_milestone_review`) rather than adding a second implementation of "how to render `{'blocked', 'no_children', <child ids>}` as one clause."

**Rationale**: The formatting logic — group `"blocked"` into `"blocked by: <ids>"`, surface `"no_children"` as-is, group every remaining entry (an outstanding child id) under one `"outstanding: ..."` clause — is presentation logic over the identical `not_ready_reason`/`blocking_ids` fields `bindle milestone review` already renders this exact way. Reusing the existing private helper (moving it, if needed, to stay importable from both call sites within `cli.py`) avoids a second, hand-copied formatter that could drift in wording from `bindle milestone review`'s own output for the identical underlying fact — the same "don't duplicate a lifecycle predicate" principle applied to its rendering, not just its computation.

## Decision: no timestamp field in the JSON contract; "as of" text stays presentation-only

**Chosen**: `WorkStatusSnapshot` and every dataclass it composes (`TaskStatusEntry`, `MilestoneStatusEntry`, `DependencyFrontier`, `ForecastEntry`) carry no "computed at"/"generated at" field. Any wall-clock context a human-facing renderer wants to show (e.g., "as of 14:32:07" in `--watch` output, or in `bindle view`'s HTML) is computed by the renderer itself at print/render time, outside the shared dataclass, and is never part of what gets `json.dumps`-ed.

**Rationale**: SC-004 requires `bindle work status --json` invoked twice against an unchanged ledger to be byte-identical. A live "generated at" timestamp embedded in the serialized snapshot would make every `--json` invocation differ from the last one by construction, directly violating SC-004 the moment it was added — this is a correctness requirement the JSON contract must satisfy, not a style preference. Keeping timestamp context entirely in the ephemeral rendering layer (never in the shared, JSON-serialized dataclass) is what makes both true at once: `--json` is exactly reproducible against unchanged state, and a human glancing at `--watch` output or `bindle view` can still see roughly when a given render happened if a future task adds that (this plan does not add it — spec.md never requires it, and it is not needed to satisfy any FR/SC/Acceptance Scenario).

## Decision: `bindle view` rendering medium — loopback `http.server` + server-rendered HTML, not a TUI (NOT ADOPTED — declined, see D045)

**Chosen**: `bindle view` starts a stdlib `http.server.HTTPServer` (not `ThreadingHTTPServer` — a single local human's browser issuing occasional sequential requests needs no concurrency) bound to `127.0.0.1` on an OS-assigned ephemeral port by default (`--port` optionally pins a fixed port). Its one `do_GET` handler, for `GET /`, calls `work_status.build_snapshot()` + `build_forecast()` fresh and returns a server-rendered HTML string (plain Python string formatting — no template engine dependency); any other path returns a plain 404. When `--watch` was given at startup, the rendered page includes `<meta http-equiv="refresh" content="{interval}">`; otherwise it is omitted entirely. `bindle view` prints the resolved URL to stdout and leaves opening a browser to the maintainer (no `webbrowser.open()` call) — a deliberately smaller surface than auto-launching a browser, which spec.md does not require and which would need its own cross-platform/`--no-open`-flag handling to keep testable and predictable in non-interactive contexts.

**Rationale — why not a `curses` TUI (stdlib, so no new dependency either)**: a curses-based renderer would still need its own input-reading loop (checking for a "refresh now" keypress without blocking), its own terminal-resize handling, and its own careful terminal-state restoration on exit or exception — genuinely more custom code than the browser option for equivalent behavior, because a browser already natively provides "reload the page" (manual refresh, FR-017) and "reload periodically" (`--watch`, FR-018) with zero Bindle-side input-handling code at all: the *identical* `do_GET` handler serves the first load, a manual reload, and every `--watch` auto-reload — there is only ever one render code path (Planning Quality Question 8's `--watch`-reuses-one-shot requirement, satisfied about as directly as it can be).

**Rationale — why not `rich`/`textual` or any packaged TUI/web framework**: `pyproject.toml` declares zero runtime dependencies today, and Technical Context across 001–004 states "None beyond the standard library" as settled, repeated precedent (`AGENTS.md`: "Inherit first. Extend second. Replace deliberately. Invent last."). Nothing about this feature's actual required behavior — one snapshot, one manual-refresh affordance, one bounded auto-refresh opt-in — needs a framework's scope; a five-ish-method HTTP handler and a string-formatted HTML page cover 100% of the Bindle-only behavior FR-016–019/022/023 require without one (Symphony composition, FR-020/021, is deferred entirely — see "Symphony endpoint discovery has no safe zero-config default," below).

**Alternatives considered**: A generic web application (client-side JS, a build step, a JSON API the page fetches from) — rejected outright per the planning brief's own explicit instruction and AGENTS.md's minimalism posture; nothing here needs client-side interactivity beyond "reload the page." Re-purposing `bindle work status --watch`'s own terminal output as `bindle view` (i.e., no separate command at all) — rejected: spec.md's User Story 5 and FR-016–019/022/023 define a genuinely separate surface (manual refresh action, explicit "small local visual surface" framing) the plain-text command was never asked to provide.

## Decision: `bindle view` keeps running as a server even without `--watch` (NOT ADOPTED — declined, see D045)

**Chosen**: `bindle view`'s process lifetime is tied to the HTTP server's own lifetime regardless of `--watch` — the server keeps `serve_forever()`-ing in the foreground until interrupted, whether or not automatic refresh is enabled. `--watch` controls only whether the *rendered page itself* asks the browser to reload periodically; it never controls whether the underlying process exits after the first render.

**Rationale**: FR-017 requires a manual refresh action "without restarting the process" — which is only possible if the process (the server) is still running when the maintainer triggers that reload. User Story 5's own Independent Test confirms this reading directly: "confirm it renders one snapshot and performs no further reads until a manual refresh is triggered" describes a process that is *waiting*, not one that has exited. "Renders exactly one snapshot... with no automatic refresh" (FR-016) describes what happens *without further action from the maintainer* — it does not mean the server itself terminates after one response.

## Decision: watch/serve shutdown behavior

**Adopted for `bindle work status --watch`; the `bindle view`/`serve_forever()` portion below is NOT ADOPTED — declined, see D045.**

**Chosen**: `bindle work status --watch`'s loop (and, as originally planned but not adopted, `bindle view`'s `serve_forever()`) both run in the main thread of the invoking process; both catch `KeyboardInterrupt` at the top level, and both exit 0 without printing a traceback. (`bindle view` would additionally have called `server.server_close()` in a `finally` block so the bound socket is released immediately rather than lingering until process teardown — moot, since no such server exists.) Neither writes to the ledger at any point, so there is no lock, temp file, or partial write to clean up on interruption (spec.md FR-010, SC-006) — this is true by construction (nothing in either code path calls a `WorkLedger` mutation method), not something this feature must separately guarantee.

**Rationale**: Directly required by spec.md FR-010 ("exit cleanly on interruption without leaving any lock, temp file, or partial output behind") and Non-Goals ("`--watch`... runs only for the lifetime of the invoking process and stops on interruption"). No daemonization, `fork()`, thread pool, or signal-handler installation beyond catching the ordinary `KeyboardInterrupt` Python already raises on `SIGINT` is needed — simplest possible shutdown path that still satisfies the requirement.

## Decision: `--watch` interval — shared default/minimum constants; single-shot `--json` vs. JSON Lines (NDJSON) in watch mode

**Adopted for `bindle work status --watch`.** (This decision's own framing anticipated a second consumer, `bindle view --watch`, sharing the same constants — that surface was evaluated and declined, see D045; `DEFAULT_WATCH_INTERVAL_SECONDS`/`MIN_WATCH_INTERVAL_SECONDS` exist and are used solely by `bindle work status --watch` in the implemented feature.)

**Chosen**: `work_status.py` defines `DEFAULT_WATCH_INTERVAL_SECONDS = 2.0` and `MIN_WATCH_INTERVAL_SECONDS = 1.0` (a caller-supplied `--interval` below the minimum is clamped up to it, never rejected outright — matching FR-011's "a sensible default and a minimum bound MUST apply when no override (or too small an override) is given").

`bindle work status --json` (no `--watch`) emits **one complete JSON document**, pretty-printed (`json.dumps(..., indent=2)`, matching `bindle repo info --json`'s existing convention). `bindle work status --json --watch` instead emits **[JSON Lines](https://jsonlines.org/) (NDJSON)** — the established term for "one complete, compact JSON value per line, newline-delimited, no enclosing array or other wrapper" — not an ad hoc or Bindle-invented streaming format. Each refresh prints exactly one line: `json.dumps(<snapshot>, separators=(",", ":"))` (compact, no `indent`, since embedded newlines inside a pretty-printed document would break the one-line-per-record framing JSON Lines depends on) followed by a single `\n`.

The **contract**, stated explicitly so it can be tested directly rather than inferred from prose:

- Single-shot `--json` (no `--watch`) emits exactly one complete JSON document conforming to `contracts/work-status-json-v1.md`, pretty-printed, and the process then exits.
- `--json --watch` emits a JSON Lines stream: one line per refresh, each line independently a complete, compact JSON document conforming to the identical `contracts/work-status-json-v1.md` shape — never a second, watch-specific schema.
- No partial JSON object is ever written. A line is only ever printed after `build_snapshot()` has returned in full and `json.dumps()` has produced the complete string — there is no code path that writes a JSON value incrementally/streamed across multiple `print()` calls.
- Within one line/document, array ordering is fully deterministic (`tasks`/`milestones` ordered by `id`, `blocking_ids` ordered by blocked-on id) — unchanged from the single-shot case; watch mode does not relax this.
- Interruption (`KeyboardInterrupt`) can only ever occur *between* two complete, already-flushed lines (during the sleep between refreshes) or *before* the current refresh's `build_snapshot()`/`json.dumps()`/`print()` sequence has produced any output at all — never mid-line. Nothing in this design holds output back to interleave with computation in a way that could leave a half-written line on interruption (research.md, "watch/serve shutdown behavior").

**Rationale for the interval numbers**: 2 seconds matches the long-established Unix `watch` command's own default cadence — a familiar, unsurprising choice for this audience (a maintainer already comfortable with CLI tools) — and a 1-second floor is enough to prevent the "unbounded-frequency reads against the ledger file" FR-011 exists to rule out, without being so conservative that `--watch` feels sluggish for a human glancing at live claim/dispatch changes during active Symphony dispatching (the motivating scenario in User Story 3's own framing). Neither number is mandated by any FR/SC — this is a planning-stage judgment call, recorded here so a future session does not re-litigate it without cause.

**Rationale for pretty vs. compact/JSON Lines**: no FR requires a specific JSON formatting style, only that `--json --watch` never produces "a partial or streamed fragment a reader must reassemble." Multi-line pretty-printed JSON has no natural inter-document boundary a streaming reader could rely on without also parsing brace-nesting; JSON Lines' one-record-per-line framing provides that boundary for free, using a well-known, already-named convention rather than an invented one.

**Alternatives considered**: A configurable delimiter line between watch refreshes (e.g., `---`) instead of JSON Lines — rejected as an invented, undocumented micro-protocol when JSON Lines is already a well-understood, named convention that requires no delimiter at all. A JSON array wrapper that grows across the whole `--watch` session (`[{...},{...},...]`, closed only on exit) — rejected outright: this is the literal "partial/streamed fragment a reader must reassemble" FR-010/US3.4 forbids, since the array is syntactically invalid JSON until the process exits and the closing `]` is written. Making single-shot `--json` also compact (for formatting consistency between watch/non-watch) — rejected: `bindle repo info --json` already establishes pretty-printed as this CLI's single-shot JSON convention, and there is no reader-facing reason a one-time script invocation needs single-line output the way a streaming reader does.

## Decision: `bindle view` process/request semantics — one long-lived server, many requests, no automatic refresh without `--watch` (NOT ADOPTED — declined, see D045)

This consolidates and makes explicitly testable what "snapshot by default" means for a process that is, mechanically, an HTTP server — the specific ambiguity this review's item 4 flagged. **"Snapshot by default" governs automatic repeated observation (polling), never the number of HTTP requests the process may serve.** Nothing in this feature's design, before or after this correction, ever limited `bindle view` to handling exactly one HTTP request — that reading is explicitly rejected below.

**Terminal attachment and startup**: `bindle view` is a foreground process, exactly like `bindle work status --watch` — it does not fork, daemonize, or detach from the invoking terminal. On startup it binds the loopback socket, prints the resolved URL (`http://127.0.0.1:<port>/`) to stdout, then calls `serve_forever()`. The maintainer's terminal is occupied for the life of the process unless they background it themselves (ordinary shell job control, e.g. `&`) — this feature adds no special backgrounding behavior of its own.

**The server handles every request it receives, for as long as it runs — not exactly one.** Its single `do_GET` handler (for `GET /`) builds a fresh `WorkStatusSnapshot` + `DependencyFrontier` and renders HTML *every time it is invoked* — once for the very first page load, once more for every subsequent manual browser reload, and, under `--watch`, once more for every automatic reload the page's own `<meta http-equiv="refresh">` tag triggers. A request to any other path (including a browser's own incidental `GET /favicon.ico`) returns a plain 404 from the same running server — an ordinary, expected request, not an error condition or a reason to stop serving. This is directly testable without pretending the process accepts only one connection: a test issuing two independent `GET /` requests against one running server instance (an initial load, then a simulated manual reload) must observe two independent, freshly-computed renders — see Technical Context, Testing.

**Manual refresh** is nothing but an ordinary browser page reload against the still-running server — no bindle-side "refresh action" code exists beyond already handling another `GET /` the normal way (this is the entire content of the earlier "`bindle view` keeps running as a server even without `--watch`" decision, restated here for completeness).

**Automatic refresh happens only under `--watch`, decided once at that invocation's own startup**: the served HTML includes `<meta http-equiv="refresh" content="{interval}">` if and only if `--watch` was passed when the process was launched; it is omitted from every response otherwise. Watch state is never persisted, never inferred, and never toggled after the process starts (FR-018) — a separate, later `bindle view` launched without `--watch` never inherits automatic refresh from an earlier launch, because there is nothing to inherit it from.

**Ctrl+C / shutdown**: identical to the existing "watch/serve shutdown behavior" decision above — `KeyboardInterrupt` caught at the top level around `serve_forever()`, `server.server_close()` in a `finally` block, exit 0, no traceback, no lingering socket or thread. Applies identically whether or not `--watch` was given, since the server's own lifetime never depended on it.

**Browser auto-opening is not part of this feature.** `bindle view` prints the resolved loopback URL to stdout; it never calls `webbrowser.open()` or otherwise launches a browser itself (restates the rendering-medium decision above, for completeness against this review's explicit checklist).

**Ephemeral/default port selection**: `HTTPServer` binds port `0` by default, letting the OS assign a free port (avoids any risk of colliding with another concurrently running `bindle view` instance for a different repository or worktree — D018's "no Bindle feature may assume one checkout per repository" applies here too); `--port` optionally pins a fixed port when the maintainer wants a stable, bookmarkable URL across relaunches.

**No non-loopback binding, by default or through any flag this feature adds**: restates the "no `--host` override" decision immediately below — `127.0.0.1` unconditionally, no way to widen it from this feature's own surface.

## Decision: no `--host` override on `bindle view` (NOT ADOPTED — declined, see D045)

**Chosen**: `bindle view` binds `127.0.0.1` unconditionally; this plan adds no `--host`/`--bind` flag of any kind.

**Rationale**: FR-019 requires no non-local exposure "by default" — but nothing in spec.md's User Stories, Acceptance Scenarios, or Non-Goals asks for an *override* of that default, and adding one would be new, unrequested surface area with real security-adjacent consequences (binding a loopback-only tool's read model, and any future Symphony composition, to a routable interface) for a "small, local, snapshot-by-default" feature explicitly scoped against becoming "a general web application." If a genuine future need for remote access appears, it is its own decision with its own threat-model discussion (`docs/PRIVACY.md`), not a flag added speculatively here.

**Alternatives considered**: Adding `--host` now, defaulting to `127.0.0.1`, "for flexibility" — rejected per `AGENTS.md`'s "invent last" posture and this project's own repeated precedent of not adding configuration surface a spec never asked for.

## Decision: Symphony endpoint discovery has no safe zero-config default — defer runtime enrichment entirely in this cut, with no placeholder (NOT ADOPTED — the whole `bindle view` surface this enrichment would have composed into was subsequently declined; see D045. **Corrected by this review.** The prior version of this decision, while correctly concluding Symphony enrichment should be deferred, still had `bindle view` render a permanent, fixed "Symphony: unavailable" section in every response — a placeholder for a reachability check that no code in this cut ever actually performs. **Grounding performed this session, directly against a local sibling checkout of the canonical `t-step/symphony` fork** (`development` @ `f0029ef` — the same 6-commits-ahead-of-pin revision spec.md's Assumptions already flagged as a known, out-of-scope documentation-currency gap): `elixir/lib/symphony_elixir/http_server.ex` starts the observability `Endpoint` only when `Config.server_port()` (from `WORKFLOW.md`'s `server.port` field, `elixir/lib/symphony_elixir/config/schema.ex`) resolves to a non-negative integer — **there is no built-in default port**; if `server.port` is unset, `start_link/1` hits its own `_ -> :ignore` branch and the dashboard/API never starts at all. `server.host` defaults to `"127.0.0.1"` (Symphony's own dashboard is loopback-only by default too, independently of this feature). This means there is no conventional port Bindle could probe as a zero-config default the way, say, a well-known service port would allow — any real endpoint-discovery mechanism requires the operator to tell Bindle where a specific running instance's `server.port` was configured (an explicit flag or environment variable), because Symphony itself has no fixed default to discover.

**Rationale for deferring rather than adding that one explicit flag anyway**: the planning brief's own decision criterion is "prefer deferral if inclusion would require meaningful new: configuration; endpoint discovery machinery... testing infrastructure" — and a genuinely working first cut needs more than just a URL flag: a bounded-timeout HTTP client call (`urllib.request`, stdlib — no new dependency, but new code), JSON-shape validation against `ObservabilityApiController`'s `/api/v1/state` payload (own-Presenter-module-owned shape, not documented as a stable external contract anywhere Bindle can cite), graceful degradation on any malformed/unreachable response (FR-021's "returns unexpected or malformed data" edge case), and a `tests/`-side fixture or fake HTTP server to exercise all of that without a real Symphony instance in CI — genuinely new configuration surface, new runtime code, and new test infrastructure, exactly the bar the brief says tips toward deferral. Implementing Bindle's own semantic surface first, fully, and correctly is the higher-value, lower-risk slice; Symphony enrichment remains a well-scoped, independently addable follow-on (FR-020 already says "MAY," not "MUST").

**What a future enrichment slice would need, recorded here so it is not re-discovered from scratch**: `GET /api/v1/state` (`elixir/lib/symphony_elixir_web/router.ex`) returns `Presenter.state_payload/2`'s JSON — running/retrying/blocked-on-input agents, workspace/worker info, last event/message (per `docs/SYMPHONY.md`'s own description, confirmed present in the controller this session) — over HTTP, JSON-encoded, on whatever `host:port` the operator's own `WORKFLOW.md` configured. No auth is visible in the router. A future slice would still need an explicit operator-supplied `host:port` (env var or flag), a short, bounded `urllib.request` timeout, and a broad `except`-and-degrade-to-"unavailable" around the whole fetch+parse, matching FR-021's graceful-degradation requirement exactly.

## Lifecycle-audit dogfooding: skill unavailable this session — manual critique performed instead

**Finding**: No `lifecycle-audit` skill is installed anywhere this session could load it from — not in this repository's `.claude/skills/`, `.agents/skills/` (both hold only the `speckit-*` family), not in the globally available-skills listing surfaced this session, and not discoverable under `~/.claude/skills/`. Per the originating task's own instruction ("If the skill is unavailable or inappropriate in the actual repository state, record that rather than approximating its behavior from memory"), this plan does not simulate or approximate a lifecycle-audit skill's output. What follows is an explicit, manually-performed critique against this feature's own four named invariants, grounded in the actual design decisions above — not a substitute claiming to be that skill's result.

**`claimed != running`**: `TaskStatusEntry.claim` (data-model.md) is sourced from `WorkLedger.get_claim()` alone — a Bindle-owned ledger fact. No field named or shaped like "running" exists anywhere in `WorkStatusSnapshot`/`DependencyFrontier`. Since Symphony enrichment is deferred entirely (previous decision) and `bindle view`'s rendered page contains no Symphony-runtime section, placeholder, or reference of any kind in this cut, there is no code path in this feature that could infer or display "running" from "claimed," because no "running" concept exists in this feature's implementation at all. This invariant is preserved by omission, not by a guard that could later be weakened by accident — worth flagging for a future Symphony-enrichment slice: that slice's own design must keep Symphony's `running`/`retrying`/`blocked-on-input` facts in a visibly distinct section (FR-020 already requires this) rather than merging them into `TaskStatusEntry`.

**`unblocked-next != dispatchable-next`**: Enforced structurally in `build_forecast()`'s `ForecastEntry` shape (data-model.md) — two separate fields, `unblocked_next: list[str]` and `dispatchable_next: list[str]` (always a subset of the former), never a single collapsed field. Verified against Acceptance Scenario US4.5 (claimed-but-blocked task) in the "forecast is a pure relate" decision above: the task lands in `unblocked_next` but is excluded from `dispatchable_next` by the `claim is None` check.

**`task dispatchable != milestone review-ready`**: Enforced at the type level — `TaskStatusEntry` has a `dispatchable: bool` field; `MilestoneStatusEntry` has a `review_ready: bool` field; there is no shared `WorkStatusEntry` base class or generic `ready`/`state` field either dataclass inherits (data-model.md's two dataclasses are structurally independent, sharing only `id`/`title`/`status`/`claim`/`blocking_ids` — every field Terminology treats as common to both kinds — and diverging exactly where the underlying concepts diverge). JSON serialization (contracts/work-status-json-v1.md) mirrors this: `tasks[].dispatchable` and `milestones[].review_ready` are distinct keys in distinct arrays, never unified into one `state` enum — directly satisfying the planning brief's explicit "do not encode `state: \"ready\"`" instruction.

**`Bindle semantic state != Symphony runtime state`**: Trivially and completely preserved in this cut, for the same reason as the first invariant — no Symphony runtime state is read, stored, or rendered anywhere by this feature. The one place this invariant will need active (not merely structural) enforcement is a future Symphony-enrichment slice, where `bindle view`'s HTML must keep the composed Symphony section visibly, textually distinguished from Bindle's own snapshot (FR-020's own requirement) rather than interleaved — recorded here as a constraint that slice inherits, not one this plan needs to enforce today.

**Conclusion**: no accidental coupling or false equivalence was found in this design — each invariant holds either structurally (distinct dataclass fields/types) or by the stronger fact that the concept it would be conflated with (Symphony's "running") does not exist anywhere in this feature's implementation yet. No plan change resulted from this critique; it is recorded as evidence the design was checked, not assumed safe.
