# Phase 0 Research: Symphony Task Integration

Every decision below was grounded this session directly against `src/bindle/work_ledger.py`, `src/bindle/cli.py`, `specs/001-durable-work-ledger/`, `specs/002-milestone-task-work-items/`, and `docs/` — not assumed. Where a claim required empirical verification (e.g. stdlib `sqlite3` read-only URI support), it was checked directly against this environment before being relied on here.

## Decision: idempotent reload mechanism

**Decision**: Derive each loaded task's `work_items.id` deterministically from its source — `speckit:{feature-directory-name}:{task-id}` (e.g. `speckit:003-symphony-task-integration:T003`) — so that re-invoking the loader against an already-loaded task attempts an `INSERT` with the same `id`, which fails on `work_items`' existing `PRIMARY KEY (id)` constraint. The loader catches that specific `sqlite3.IntegrityError` (checked via `exc.sqlite_errorcode == sqlite3.SQLITE_CONSTRAINT_PRIMARYKEY`, the same discrimination technique `claim()` already uses to distinguish "already claimed" from every other integrity failure) and treats it as "already loaded" — a normal, expected outcome, not an error surfaced to the caller.

**Rationale**: `create_work_item()` has no existing uniqueness check on `(source_kind, source_locator)` at write time — confirmed by reading the actual `INSERT` statement and schema directly this session; the only place a duplicate source is ever detected is `reconcile()`'s read-only, after-the-fact `duplicate_source` finding (`data-model.md`: "No uniqueness constraint on `(source_kind, source_locator)`, deliberately"). A loader that relied on that finding would have to run a full reconciliation before every load and would still race against a concurrent second invocation. A loader that instead ran "does a work item with this `source_locator` already exist?" as a separate `SELECT` before its own `INSERT` would reintroduce exactly the check-then-act race window `work_ledger.py`'s own commentary repeatedly calls out as the class of bug `BEGIN IMMEDIATE` and guarded `UPDATE...WHERE` patterns exist to close (see `mark_in_review`'s and `create_work_item`'s own parent-openness check, both explicitly reasoned about this way). Deterministic-id-plus-PK-collision has neither problem: the primary key itself is the sole arbitration mechanism, exactly mirroring `claim()`'s own "the row's existence, not a separate check, decides the outcome" design (`contracts/work-item-record.md`'s claim guarantees).

**Alternatives considered**:
- *Query-then-create by `source_locator`.* Rejected: introduces a race window between the existence check and the `INSERT` under concurrent loader invocations, and duplicates the "is this thing already claimed by an equivalent identity" logic `claim()` already solves at the schema level for a different table — no reason to solve it worse a second time.
- *Caller-supplied, arbitrary `id` with a separate application-level dedup table.* Rejected: adds a second table purely to reconstruct a lookup SQLite's own `PRIMARY KEY` index already provides for free once the id is deterministic; contradicts `AGENTS.md`'s "extend before replace" and this ledger's own "handful of narrow methods over plain SQL" posture.
- *Rely on `reconcile()`'s `duplicate_source` finding as the idempotency gate.* Rejected: that finding is explicitly documented as visibility, not prevention (`data-model.md`), is read-only, and only runs when a caller explicitly asks for it — using it as a load-time gate would require an extra full-ledger scan on every load and still leaves the actual `INSERT` racy.

## Decision: stable source identity scheme

**Decision**: `source_kind = 'speckit_task'` (already reserved in the schema's `CHECK` constraint, unused until now); `source_locator = "{feature-directory}/tasks.md#{task-id}"` using the feature directory's path relative to the repository root (e.g. `specs/003-symphony-task-integration/tasks.md#T003`) — exactly the example format `specs/001-durable-work-ledger/data-model.md`'s own "Source Reference" section already documents (`specs/001-durable-work-ledger/tasks.md#T012`).

**Rationale**: Spec Kit's own task ids (`T001`, `T002`, ...) are unique only within one feature's `tasks.md` — confirmed this session by reading `.specify/scripts/bash/create-new-feature.sh` (which numbers the feature *directory*, never a task id) and both existing `tasks.md` files (both independently start at `T001`). Combining the feature-directory path with the task id is the smallest identity that is actually stable: the directory name is fixed once a Spec Kit feature is created (`create-new-feature.sh` never renumbers an existing directory), and reusing the exact format `data-model.md` already documents as an example means no new provenance convention is invented — this loader is the first caller to actually populate the pattern the schema's own docs already anticipated.

**Alternatives considered**:
- *Task id alone (`source_locator = "T003"`).* Rejected outright: collides across every feature directory, which is precisely the ambiguity this decision exists to avoid.
- *A synthetic UUID per task, with the feature/task pointer stored as a separate field or in `description`.* Rejected: invents a second identity scheme where `source_locator`'s own documented, pointer-shaped format already suffices; would also fail SC-004's zero-collision requirement no more cleanly than the chosen format, while adding an opaque id nothing else in the ledger uses.

## Decision: how a reload updates an existing work item

**Decision**: Add `WorkLedger.resync_declarative_fields(id, title, description) -> bool` — a new, generic, single guarded `UPDATE work_items SET title = ?, description = ?, updated_at = ? WHERE id = ? AND archived_at IS NULL`, returning whether it matched a row. This is the *only* mutation a reload performs on a work item whose id it already recognizes; `status`, `work_item_claims`, and `work_item_evidence` are never touched by it, and it is added to `work_ledger.py` rather than a new module because it operates directly on the canonical schema exactly like every other guarded-transition method there.

**Rationale**: No existing `WorkLedger` method updates `title`/`description` on an existing row — `create_work_item()` is create-only, and every other write method is a status/claim/evidence transition, not a text update. spec.md's FR-007/FR-008 require title/description to be re-syncable and `blocked_by` edges to be additive-only on reload; a single narrow method that touches exactly those two text columns (plus `updated_at`, matching every other mutator's own convention) is the smallest addition that satisfies both without opening a path to mutate anything runtime-owned. Guarding on `archived_at IS NULL` mirrors `mark_done`'s own "guarded transition, not an error, when it doesn't apply" convention — resyncing an archived item's already-thinned row would be meaningless (its `title`/`description` are already `NULL` by archival's own design) and is a true no-op here, not a failure.

**Alternatives considered**:
- *A generic `update_work_item(id, **fields)` accepting arbitrary column names.* Rejected: this is exactly the "arbitrary mutation surface" this feature's own FR-023 (for the external write surface) and this ledger's whole design (guarded, single-purpose methods, never a generic setter) argue against, even for an internal caller — it would let a future caller silently mutate `status` or `source_kind` through the same path.
- *Delete-and-recreate the work item on reload instead of resyncing in place.* Rejected outright: violates FR-006/SC-002/SC-003 directly — deleting a row that already has claims/evidence attached is exactly the "reset runtime-owned state" this feature must never do, and the schema's own foreign keys (`work_item_claims`, `work_item_evidence`, `work_item_blocked_by` all reference `work_items.id`) would make this destructive in ways `resync_declarative_fields` never risks.

## Decision: dependency loading order within one feature directory

**Decision**: The loader processes a feature directory's `tasks.md` in two passes within one invocation — pass 1 creates or resyncs every parseable task's own work item (no `blocked_by` edges yet); pass 2 adds every declared `Depends on: T00X` edge, translating each `T00X` reference to that same feature directory's own deterministic id and calling `WorkLedger.add_blocked_by()` (already idempotent-if-called-again in spirit, though not literally idempotent at the SQL level — see below) for any edge not already present.

**Rationale**: A single-pass, in-file-order loader would fail whenever a task's `Depends on:` line names a task id appearing *later* in the same file (spec.md FR-009 requires this to resolve regardless of line order) — `add_blocked_by`'s own foreign-key constraint would reject a reference to a row that doesn't exist yet. Two passes make ordering irrelevant without needing to topologically sort `tasks.md`'s own free-text dependency prose. `add_blocked_by()` has no `INSERT OR IGNORE` behavior of its own (a second identical edge is a plain `PRIMARY KEY (work_item_id, blocked_on_id)` violation) — the loader's pass 2 first reads the task's already-recorded edges (a work item's dependency set is small; no new bulk-read method is needed, a plain per-item query suffices) and only calls `add_blocked_by()` for an edge not already present, satisfying FR-008's "may add, must never remove" without adding a new ledger primitive for "idempotent add."

**Alternatives considered**:
- *Require `tasks.md` dependencies to always reference an earlier line.* Rejected: this is not actually true of the existing `tasks.md` files this session read (a later phase's task can depend on an earlier one, but nothing in Spec Kit's own template enforces monotonic ordering by id), and enforcing it would make the loader reject real, currently-valid task lists for a reason that has nothing to do with their correctness.
- *Add a new `WorkLedger.add_blocked_by_if_absent()` method.* Rejected as unnecessary: a read (`is_blocked`-adjacent per-item edge query) plus the existing `add_blocked_by()` is already a two-statement, non-atomic-but-harmless sequence — worst case under a genuinely concurrent double-load, the second caller hits a duplicate-edge `IntegrityError`, which the loader already needs to tolerate as "someone else already added this edge" (parallel to the `id`-collision tolerance above), so a new ledger primitive buys nothing a caller-side catch doesn't already provide.

## Decision: published projection storage location and format

**Decision**: A **separate, disposable, regenerated `.sqlite3` export file** — not a `CREATE VIEW` inside the existing internal `ledger.sqlite3`. The file lives at `{repo_root}/.bindle-work/symphony-projection.sqlite3` (a sibling of `ledger.sqlite3` under the same `.bindle-work/` directory `ledger_path()` already establishes, resolved from `RepoInfo.repo_root` — the Git common directory — so every linked worktree sees the same published artifact, exactly like the internal ledger). It contains exactly one table, `task_projection`, holding the shape `data-model.md` defines, fully rewritten (drop-and-recreate, inside one transaction) on every publish — never incrementally patched.

**Rationale**: This session verified empirically, against this exact environment (SQLite 3.53.4, the same version `work_ledger.py`'s own comments already cite as their baseline), that stdlib `sqlite3` supports a genuine read-only connection via `sqlite3.connect("file:...?mode=ro", uri=True)`. That made a `CREATE VIEW` inside the internal file a technically real option — but it was rejected on `docs/PHILOSOPHY.md`/`docs/DATA-OWNERSHIP.md` grounds, not technical ones: a view inside `ledger.sqlite3` would mean an external reader connects directly to Bindle's own canonical storage file, coupling that external reader to whatever internal schema exists at any given `_SCHEMA_VERSION` — exactly the "Bindle's durable outputs are embeddable artifacts, not destinations" and "everything derived must be rebuildable from a durable source" framing (`docs/PHILOSOPHY.md` D014/D015, `docs/DATA-OWNERSHIP.md` "Durable versus derived") argues against for anything meant to be an external contract. A wholly separate file, regenerated on demand from the canonical tables, keeps the internal schema free to evolve (a future `_SCHEMA_VERSION` bump never breaks an external reader, since the reader never sees the internal file at all) and matches this feature's own contract docs' framing of a projection as "a generated, disposable file (or command output)" — language `specs/001-durable-work-ledger/contracts/coordinator-projection.md` already used for the in-process projection, now made literal for this one.

**Alternatives considered**:
- *`CREATE VIEW` inside `ledger.sqlite3`, opened `mode=ro` externally.* Rejected: couples an external reader to Bindle's own internal file and schema-version lifecycle directly — the one thing D014's replaceability rule and this ledger's own "never a Symphony adapter" boundary both argue against. Also complicates the internal file's own write path for no benefit (WAL mode, foreign-key pragmas, and schema migrations would now have to consider an external, ungoverned reader connected to the same file at arbitrary times).
- *JSON export instead of SQLite.* Rejected: the feature's own brief explicitly asks for a "Bindle-owned SQLite Symphony projection," and Symphony's own shipped local tracker already reads JSON (`.symphony/local_tracker.json`, per `docs/SYMPHONY.md`) — duplicating that format would not add a new capability, only a second, redundant JSON artifact; a SQLite export is a genuinely different, queryable shape a JSON file doesn't offer as directly (arbitrary `WHERE` filtering by any external tool without a bespoke parser).

## Decision: published projection versioning

**Decision**: The export file carries its own `PRAGMA user_version` (starting at `1`), set inside the same transaction that rewrites `task_projection`, entirely independent of the internal ledger's `_SCHEMA_VERSION`. `contracts/symphony-projection-v1.md` documents version 1's exact shape; a future incompatible shape change ships as `symphony-projection-v2.md`, mirroring the `coordinator-projection.md` → `coordinator-projection-v2.md` precedent `specs/002` already established, alongside a bump of the exported file's own `user_version`.

**Rationale**: `PRAGMA user_version` is the same zero-dependency, SQLite-native mechanism `work_ledger.py` already uses for its own internal schema versioning (`_SCHEMA_VERSION`) — reusing the identical mechanism for a second, independent artifact is the smallest possible addition, and it means an external reader can determine the projection's version with a single `PRAGMA user_version` query against the export file alone, satisfying FR-018's "discoverable without inspecting Bindle's internal tables" (the export file *is* the only thing the external reader ever opens).

**Alternatives considered**:
- *A `meta` table with a `version` row inside the export file.* Rejected: `PRAGMA user_version` already does exactly this with zero schema overhead and no extra table to keep in sync with the real data table; no reason to reinvent it a second way in a codebase that already has one working convention for it.
- *Version the export file's *name* instead (e.g. `symphony-projection-v1.sqlite3`).* Rejected: would require every consumer to know the current version's filename in advance and would leave stale versioned files behind on every schema bump; an in-file `PRAGMA user_version` lets the file's own name stay stable while its content's version is queryable from inside.

## Decision: `identifier` derivation for external workspace naming

**Decision**: `identifier` is the work item's own `id` with `:` replaced by `-` (e.g. `speckit:003-symphony-task-integration:T003` → `speckit-003-symphony-task-integration-T003`) — deterministic, always non-empty (since `id` is never empty, per the schema's `PRIMARY KEY NOT NULL` semantics), and filesystem/shell-safe for use as a directory or branch-name component.

**Rationale**: spec.md FR-015 requires "a non-empty identifier suitable for external workspace naming." The work item's own `id` already satisfies uniqueness and non-emptiness; the only adjustment needed is removing a character (`:`) that is awkward in shell arguments, directory names, and some Git branch-name conventions. Deriving `identifier` from `id` by a fixed, reversible-in-spirit (though not required to be reversed) transformation avoids introducing a second independent identity a caller could observe drifting from the first.

**Alternatives considered**:
- *Use the bare Spec Kit task id (`T003`) as `identifier`.* Rejected: fails uniqueness the moment two loaded features both have a `T003` — reintroduces exactly the collision problem the source-identity decision above exists to close.
- *A separate, independently-assigned short code.* Rejected: adds a second id-allocation concern (uniqueness tracking, persistence) for no benefit over a pure, stateless string transform of the id that already exists.

## Decision: write-surface exposure — both library and CLI

**Decision**: `claim_task(ledger, id, owner, worktree_path=None, branch=None)`, `release_task(ledger, id, owner)`, and `complete_task(ledger, id)` are ordinary Python functions in `src/bindle/symphony_projection.py`, each fetching the work item first to reject a `type='milestone'` id (FR-024), then delegating to `WorkLedger.claim()`/`release_claim()`/`mark_done()` unchanged. `src/bindle/cli.py` gains a `bindle work` command family (`claim`, `release`, `done`, plus `load-speckit` and `publish` for the other two stories) whose `_cmd_work_*` handlers call these same functions and translate the result to the existing 0/1 exit-code, `bindle work <verb>: ...`-stderr convention `_cmd_repo_info`/`_cmd_skills_*` already establish.

**Rationale**: spec.md's own Assumptions left this open as a planning-phase decision. Library-only would satisfy every functional requirement but would leave "an external coordinator" needing to embed a Python import to use Bindle at all — inconsistent with every other Bindle-owned operational surface (`guardrails`, `projectmem`, `qmd`, `skills`) already being reachable through `bindle` as a plain CLI subprocess, which is the integration shape an external, non-Python coordinator (Symphony's own Elixir runtime) actually needs. CLI-only would make the functions untestable as ordinary Python and unusable by a future in-process caller. Both, with the CLI as a thin translation layer over the library functions, is the shape every existing `bindle` command family already uses (e.g. `skills/catalog.py`'s `add()`/`remove()` functions plus `cli.py`'s `_cmd_skills_add`/`_cmd_skills_remove` wrappers) — no new pattern invented.

**Alternatives considered**:
- *CLI-only, with the logic inlined directly in `_cmd_work_*` handlers.* Rejected: duplicates exactly the "logic lives in a testable function, CLI is a thin wrapper" split every other command family in `cli.py` already uses, and would make a future non-CLI caller (e.g. a Python-native worker harness `docs/SYMPHONY.md` acknowledges as a future possibility) unable to reuse the write surface without shelling out to itself.

## Decision: `tasks.md` line parsing strategy

**Decision**: A narrow, regex-based line parser recognizing exactly the shape both existing `tasks.md` files use: `- [ ]` or `- [x]` (checkbox state ignored, per spec.md FR-012), followed by `T\d{3}[a-z]?` (matching the `T016a`-style suffix already observed in `specs/002-milestone-task-work-items/tasks.md`), an optional bracketed story tag (`[US1]`, `[P]`, etc., ignored), then free-text description, with an optional trailing `Depends on: T\d{3}[a-z]?(?:, T\d{3}[a-z]?)*\.` clause extracted separately. Everything outside this exact shape (section headers, the "Dependencies & Execution Order" prose section, blank lines, the file's own front-matter) is skipped without error — only lines that look like they were *trying* to be a task line but don't fully match are reported as FR-011's "skipped, with a clear reason."

**Rationale**: This session confirmed no machine-parseable structure exists in `tasks.md` beyond this one line shape — dependencies are free-text prose, not a structured field, and no Python code in the repository parses this file today. Building a general Markdown parser (headers, lists, tables) would be solving a problem this feature doesn't have and directly contradicts spec.md's own framing ("not a general Markdown workflow engine") and `AGENTS.md`'s "Do not build a general Markdown workflow engine." A fixed-shape regex is the smallest correct tool for one well-understood, stable line format.

**Alternatives considered**:
- *A general Markdown AST parser (e.g. treating the file as a list of list-items).* Rejected: adds a new dependency (this repo has zero today) to parse structure the task lines don't actually need — a checkbox list item's own Markdown semantics (nesting, inline formatting) are irrelevant to extracting an id, a title, and a dependency clause from one line of known shape.
- *Require `tasks.md` to declare a machine-readable dependency block (e.g. YAML front matter) as a prerequisite for loading.* Rejected: would require changing `speckit-tasks`' own template and every existing `tasks.md` file to be loadable at all, directly contradicting this feature's own framing of loading a decomposition Spec Kit already produced as-is ("faithfully persists declared work rather than inventing new planning semantics").

## Decision: `docs/SYMPHONY.md` update scope

**Decision**: Update exactly two sentences in the "Non-scope" section once this feature lands — the "create, read, or translate work items for any Symphony tracker" clause and the "couple its own SQLite work-item model... to Symphony's tracker/storage... in any way" clause — replacing both with an accurate, narrow statement that Bindle now publishes a documented, versioned SQLite projection and a narrow write surface, while still not installing, running, or building a Symphony-specific tracker adapter. Add a new short section (mirroring how `specs/002`/D038 added the existing "Scheduling boundary" section to the same document) pointing at `contracts/symphony-projection-v1.md` and `contracts/task-write-surface.md` as the canonical reference for what actually exists. Leave "Canonical repository," "Pinned reference," and "What Symphony requires before first execution" completely untouched — this session's own investigation confirmed those describe facts about Symphony itself, unaffected by anything this feature does.

**Rationale**: This session's own audit found these exact two sentences would become false the moment this feature ships (task creation/translation and SQLite-to-tracker coupling are precisely what the loader and the published projection do), while everything else in the document remains accurate. Editing only the stale sentences, in place, mirrors this repository's own append-only-but-corrected convention for `docs/DECISIONS.md` and the precedent `specs/002` already set for this exact document when D038 landed.

**Alternatives considered**:
- *Leave `docs/SYMPHONY.md` unchanged and let the drift stand.* Rejected: `AGENTS.md`'s evidence-discipline and this repository's own decision-log conventions require documentation to track what's actually true; a stale "Bindle does not create or translate work items for Symphony" sentence sitting next to code that does exactly that is a documentation defect this feature itself introduces if left unfixed.
- *Rewrite `docs/SYMPHONY.md` from scratch.* Rejected: the majority of the document (canonical repo, pin, Symphony's own toolchain requirements, the existing "Scheduling boundary" section) remains accurate and is evidence gathered in prior sessions — rewriting it would discard that provenance for no benefit over a targeted, in-place correction.
