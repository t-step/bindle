# Contract: Coordinator Projection (Symphony-facing, generated view)

This documents the minimum contract a future projection step owes to a future coordinator (Symphony, or a replacement) — not an implementation, and not a commitment to build the projection or the Symphony adapter now (both remain explicitly out of scope for this feature, per the task brief). Field mapping below is grounded in the pinned Symphony fork's own source, not the stale exploration plan (see research.md, "Decision: projection contract with Symphony").

## What the projection is

A generated, disposable file (or command output) derived entirely from current Work Item records at generation time. Regenerating it twice from unchanged Work Item state MUST produce an equivalent result (spec.md SC-005) — it is never itself a durable input to anything.

## Minimum facts required, and where they come from

| Coordinator-facing fact | Derived from | Notes |
|---|---|---|
| A stable identifier | Work Item `id` | Symphony's `Tracker` behaviour requires `id`/`identifier` to be non-empty strings (`SPEC.md` §11.3). |
| A human-readable title | Work Item `title` | Required non-empty per `SPEC.md` §11.3. |
| A state string that is a member of the target WORKFLOW.md's `active_states`/`terminal_states` | Work Item `status` plus the *derived* Blocked/Available facts | `open` maps to whichever `active_states` string the target WORKFLOW.md declares; `done`/`superseded` map to a `terminal_states` string. These strings are arbitrary per-deployment configuration (research.md finding), not fixed by this contract. |
| Per-item eligibility | Work Item's derived "Available to start" fact (data-model.md) | **Load-bearing finding**: Symphony's shipped `local` tracker adapter hardcodes `dispatchable: true` and does not evaluate `blocked_by` itself. The projection step MUST therefore withhold a still-blocked item from any `active_states` value entirely (or otherwise ensure it is not treated as eligible) — Symphony will not do this filtering for us on the `local` adapter path. Resolving each `blocked_by` entry for this computation follows data-model.md's "Dependency resolution" — a single-table lookup against `work_items` that resolves identically whether the referenced item is still active or has been archived and thinned in place, since its `status`/`superseded_by` columns are never cleared by archival. A prerequisite archived before projection time is therefore still correctly resolved as satisfied, never mistaken for a dangling/unknown reference. A currently-claimed item is also withheld regardless of blocking state, per the same "Available to start" definition — claimed work is never presented to a coordinator as eligible to (re)dispatch. **Withholding is not simply "keep it out of `active_states`"**: `active_states` and `terminal_states` are two independently-configured membership sets with no implicit third "withheld" status (`plans/active/2026-08-24-symphony-coordination-exploration.md`'s Evidence, verified against the pinned fork's `orchestrator.ex`) — an item's projected state string must not land in `terminal_states` either, since the item is neither done nor superseded. A future projection either omits a not-currently-eligible item from the generated file entirely, or assigns it a state string that is a member of neither configured set; this contract does not choose between those two mechanisms, only rules out the third option (a state that is, or could be read as, a member of either set). |
| Ordering hint (optional) | Not derived from anything in this ledger | This ledger has no priority/ranking concept (FR-015) and none is invented for this contract. If the target WORKFLOW.md's tracker expects a `priority` field, an unset/null value is acceptable — Symphony's own `priority_rank/1` ranks unset priorities last, never treats them as an error. |
| Optional dashboard/log fields (`branch_name`, `url`, `description`, `labels`) | Work Item's Evidence Pointers / `title` / none | **Confirmed not load-bearing**: `branch_name` has zero workspace-routing call sites in the pinned fork; `url` is display-only. A projection MAY populate these for human convenience but MUST NOT rely on Symphony reading them for execution routing. |

## What the projection explicitly does not do

- It does not compute a dispatch order, retry policy, or concurrency limit — those remain entirely Symphony's own orchestrator responsibility (`orchestrator.ex`), untouched by this contract (FR-015, exploration plan's own settled direction).
- It does not write back into the Work Item ledger from Symphony's own state — this contract is one-directional (ledger → projection). Reconciling Symphony's post-execution outcome back into the ledger is explicitly future work, deferred until the first vertical proof exists (mirrors the exploration plan's own bootstrapping posture: "Work items are loaded into SQLite manually for now," translated to whatever format this plan's ledger actually uses).
- It does not assume Symphony, or any particular tracker adapter, is installed — the ledger and every guarantee in `work-item-record.md` hold with zero coordinator present (spec.md User Story 4, Acceptance Scenario 3).
- **It does not guarantee that a coordinator observes any particular ledger state, including a terminal (`done`/`superseded`) transition, before that item is archived.** A projection is a disposable snapshot of current ledger state at generation time — never an event stream, delivery protocol, or acknowledgment mechanism. Completion becomes authoritative in the ledger the instant a Work Item's `status` changes to `done` or `superseded`; Bindle's own archival rules (`research.md`, "Decision: retention") apply independently of whether, or how many times, a coordinator projection of that item was ever generated beforehand. If a projection happens to run while the terminal Work Item's row is still fully populated (not yet archived), it may represent the item as terminal per the field mapping above; if the item is archived (thinned) first, a later projection is not required to reconstruct or replay that transition from the row's surviving columns (data-model.md's "Archival" section keeps `id`/`status`/`superseded_by` resolvable to keep dependency resolution and supersession linkage correct, not to serve as coordinator-facing delivery history). A future integration that genuinely needs guaranteed transition delivery is a separate integration concern — this contract does not acquire acknowledgment state, projection cursors, or similar machinery to approximate one.
