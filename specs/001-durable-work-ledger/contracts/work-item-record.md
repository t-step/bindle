# Contract: Work Item Record (agent/human-facing)

This is the contract an agent or maintainer reads/writes against — not a code interface (no ledger code exists yet). It documents the guarantees a future implementation must uphold, derived from data-model.md and spec.md's functional requirements.

**2026-08-26 persistence-model correction**: every guarantee below is restated against the SQLite relational model in `data-model.md` (single database file, `work_items`/`work_item_blocked_by`/`work_item_claims`/`work_item_evidence` tables) in place of the original per-item-file model. The *guarantees themselves* — what an agent may rely on — are unchanged in substance except where noted; only the mechanism providing each one changes.

## Read guarantees

- Listing all work items MUST be possible from any linked worktree of the repository, with identical results, at a given point in time (FR-011; resolved storage location: the Git common directory, research.md) — every linked worktree opens the same physical SQLite file.
- Reading a single item by `id` MUST return the same record structure regardless of which worktree or session performs the read.
- Computing "available to start" (data-model.md's derived fact) for the full set of items MUST NOT require any live process, network access, or coordinator (FR-012) — it is a single `SELECT` query against the local database file.
- A stale or corrupt claim (data-model.md's "Claims" section) MUST be discoverable by inspecting only: the claim row's own recorded `worktree_path`/`branch` and readability, and currently observable repository/filesystem state — no external service call.
- Resolving whether a work item's declared blocking relationship is currently satisfied MUST be possible by checking only `work_items` (data-model.md's "Dependency resolution") — a single-table lookup that resolves identically whether the referenced item is still active or has been archived and thinned, since archival never removes a row or clears its `status`/`superseded_by` columns.
- Direct SQL inspection of the ledger — via the `sqlite3` CLI, or any general-purpose SQLite client — MUST remain possible without going through Bindle's own code, as a supported operational property (`research.md`, "Decision: corruption, recovery, and inspectability"), not merely an accidental side effect of the file format.

## Write guarantees

- Creating a Work Item is only ever performed by an explicit act naming a Source Reference (FR-002/FR-003) — there is no operation that creates a Work Item without one.
- Two different Work Items MUST be independently writable without one write affecting the other's stored record (SC-004) — this is provided by ordinary row-level independence within the `work_items` table under SQLite's transaction isolation, not by a locking layer Bindle's own code implements.
- Marking an item `done` or `superseded` MUST NOT delete its record outright; a `superseded` item retains `superseded_by` (FR-016, enforced by `work_items`' own `CHECK` constraint pairing the two columns), and archiving it MUST thin the row to its permanent columns (`id`, `status`, `superseded_by`, `archived_at`) within a single transaction that also removes its evidence, its own declared `blocked_by` edges, and any lingering claim — never as two separately-timed operations that could leave a gap between them (FR-020, data-model.md's "Archival").
- No write operation defined by this contract computes or persists a dispatch order, priority rank, or concurrency assignment among items (FR-015) — those remain absent from the schema entirely; no column exists to hold one.
- A `blocked_by` edge naming a nonexistent work item id is rejected at write time by the `work_item_blocked_by` table's own foreign key constraint (when the connection has `PRAGMA foreign_keys = ON`, which is mandatory — `research.md`, "Decision: connection lifecycle") — a stronger, earlier guarantee than the original file-based model offered, where such a mistake could only be discovered later by reconciliation. This narrows, but does not eliminate, the `dangling_blocker` reconciliation finding — see data-model.md's "Dependency resolution."

## Claim guarantees (FR-018, FR-019 — the precise concurrency contract)

- **Acquiring a claim MUST be a single atomic, exclusive insert-if-absent operation against a claim row dedicated to that item's id — never a read-then-write against the Work Item's own row or any shared row.** Of any number of concurrent acquire attempts for the same item, exactly one MUST succeed; every other MUST receive an immediate, deterministic "already claimed" failure — not a timeout, not an ambiguous result, and never a window in which more than one attempt could believe it succeeded. Under the SQLite model this is provided directly by the primary key on `work_item_claims.work_item_id`: a losing `INSERT` fails with a constraint violation. This is precise enough to test deterministically: spawn N concurrent acquire attempts against one never-before-claimed item id and assert exactly one success and N−1 identical, immediate failures, repeated across many trials (SC-004a).
- **The claim row's existence, not its content, is what decides ownership.** Under the SQLite model, a single `INSERT` statement is transactionally atomic: it either commits with every `NOT NULL` column populated, or is rolled back entirely and the row does not exist. There is therefore no reachable state, via an ordinary application crash during acquisition, in which a claim row exists but is missing its content — a genuine strengthening over the original file-based contract's crash window, not merely a change of representation. `corrupt_claim` remains a defined finding for the narrower cases that can still produce an inconsistent row (database-file-level corruption, or a connection that ran with constraints bypassed); when it does occur, the row MUST still be treated as claimed (never as available), and MUST be surfaced distinctly rather than trusted as a normal, attributable claim.
- **Releasing a claim is deleting its row.** Releasing an already-released (nonexistent) claim MUST be a no-op, not an error. Release by the recorded owner MUST always be permitted. Release by anyone else (an override) MUST only be performed on the basis of an observed `stale_claim` or `corrupt_claim` reconciliation finding for that specific item — never automatically, never on a timer.
- **Reconciliation finding a claim stale or corrupt MUST NOT itself release it or change the item's computed availability** — the item remains unavailable until the explicit override above is performed (FR-010). Reconciliation performs only `SELECT` queries against the ledger; it never opens a write transaction.

## Transaction guarantees

- Any mutation that changes more than one related, durable fact in one logical action (declaring several `blocked_by` edges at item creation; archiving a terminal item, which clears columns and deletes evidence/edges/claim together; releasing a claim together with an optional Evidence Pointer documenting the override) MUST run inside a single database transaction, so that a crash or interruption mid-mutation leaves the ledger in exactly its pre-mutation state — never a partially-applied one. See `research.md`'s "Decision: transaction boundaries" for the exact statement-level boundary of each defined mutation.
- No mutation defined by this contract spans more than one work item's own claim as a single all-or-nothing operation — see "Non-goals" below.

## Non-goals of this contract

- No transactional multi-item write ("claim these three items atomically, or none") is guaranteed or required — only single-item claim acquisition is covered by the atomicity guarantee above, even when several items' claims happen to be attempted within the same call.
- No automatic lease, heartbeat, or timeout-based claim expiry is defined or implied — staleness is determined solely by checking observable repository/filesystem state at the moment reconciliation runs, on demand, never by elapsed time.
- No network-facing API is defined — this is a local database contract, consistent with `docs/SCOPE.md`'s "Bindle does not own... generic project management" as a hosted concept. No client-server database, connection pool, or daemon process is implied by "database" here — see `research.md`'s "Decision: connection lifecycle" for the short-lived, per-operation connection model this contract assumes.
