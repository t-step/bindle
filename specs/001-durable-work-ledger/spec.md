# Feature Specification: Durable Work Ledger

**Feature Branch**: `spec/durable-work-item-model`

**Created**: 2026-08-26

**Status**: Draft

**Input**: User description: "Durable implementation-work model: a repository-local, Bindle-owned coordination ledger that lets decomposed implementation work survive individual agent sessions, worktrees, branches, context loss, and ordinary Git weirdness. The ledger holds small orthogonal coordination facts per work item (status, blocking, ownership/claim, evidence pointers, source pointer back to the spec/plan/task that produced it) rather than a large lifecycle state machine. It is the durable pre-scheduling source of truth that a future Symphony projection is generated FROM (materialized on demand into whatever a specific tracker adapter needs, e.g. Symphony's local JSON tracker) — Symphony remains the execution coordinator and is never the authoritative ontology for this ledger. Spec Kit specs/plans/tasks remain the upstream source of intent; promoting a task into a durable ledger item is a deliberate, explicit act, not automatic. This is a specification-only feature: no ledger code, no bindle init wiring, and no Symphony adapter implementation are in scope — only the durable data model, its ownership boundary relative to Bindle's stateless-toolchain-bridge philosophy, its reconciliation-against-git-state semantics, and the minimum projection contract a future Symphony integration would consume."

### User Story 1 - Decompose accepted work into durable items (Priority: P1)

An agent has an accepted spec, plan, or task list (from Spec Kit or an ad hoc plan under `plans/`) and needs to break it into units of work that can each be picked up, claimed, and finished independently — and that will still exist, intelligibly, if the current session ends, the context window resets, or a different agent opens a different worktree tomorrow.

**Why this priority**: Without a durable record that a unit of work exists and what state it's in, decomposition value is lost every time a session ends. This is the foundation every other scenario depends on.

**Independent Test**: Create several work items from a plan's decomposition, end the session, and confirm — from a fresh session with no memory of the first — that the same items, with the same identity and source pointer, are still discoverable and intelligible.

**Acceptance Scenarios**:

1. **Given** an accepted plan or spec task describing a bounded piece of work, **When** an agent promotes it into the ledger, **Then** a durable work item is created carrying a stable identifier, a human-readable summary, and a pointer back to the spec/plan/task it came from.
2. **Given** a durable work item already exists, **When** a new session with no prior context inspects the repository, **Then** the item's identity, source pointer, and current coordination facts (status, blocking, claim, evidence) are fully recoverable without any information from the session that created it.
3. **Given** a Spec Kit `tasks.md` containing many tasks, **When** no agent has explicitly promoted any of them, **Then** the ledger contains no items for that feature — task generation alone never creates ledger items.

---

### User Story 2 - Resume and determine what's actually available (Priority: P1)

An agent (the same one resuming after a break, or a different one entirely) needs to know, without any live coordinator process and without re-deriving it from scratch, which recorded work items are currently safe to start: not already claimed, not blocked on unfinished work, and not already done or superseded.

**Why this priority**: This is the entire point of durability — an agent must be able to answer "what can I work on right now" purely from repository state, at any time, from any worktree.

**Independent Test**: Construct a ledger containing a mix of open/unclaimed, open/claimed, blocked, done, and superseded items, including at least one chain of two or more blocking relationships, and confirm that the set of items correctly identified as "available to start" excludes every claimed, blocked, done, and superseded item and includes every other one.

**Acceptance Scenarios**:

1. **Given** a work item recorded as blocked on another item that is not yet done, **When** an agent asks whether that item is available to start, **Then** the answer is no, and the reason (which unresolved item is blocking it) is discoverable.
2. **Given** a work item that is not blocked and not claimed, **When** an agent asks whether it is available to start, **Then** the answer is yes.
3. **Given** an item marked done, **When** another item's blocking relationship names it, **Then** the second item is no longer considered blocked on that account.

---

### User Story 3 - Claim, work, and reconcile across worktrees without collision (Priority: P2)

Two agents (or the same agent across two sessions) work on two independent items at the same time, each in its own worktree and branch, per this repository's own development-isolation policy. Each claim, and eventually each item's completion evidence, must be attributable and must not corrupt or silently overwrite the other's record. When a claimed item's worktree disappears (deleted, abandoned, never pushed), that fact must become visible rather than being silently trusted.

**Why this priority**: Concurrent, worktree-isolated work is this repository's normal operating mode (`AGENTS.md`, "Development isolation"); the ledger must not assume a single active worktree or a single active agent.

**Independent Test**: Record two claims against two different items from two different (simulated) worktrees, confirm neither claim affects the other item's record, then delete one claimed item's worktree/branch and confirm that reconciliation against actual repository state flags that claim as stale rather than treating the item as still in progress or, worse, as done.

**Acceptance Scenarios**:

1. **Given** two independent, unclaimed work items, **When** two agents each claim a different one, **Then** each item records its own claim (who, when, and — when applicable — which branch/worktree) independently of the other item.
2. **Given** a claimed item whose recorded worktree or branch no longer exists, **When** reconciliation runs, **Then** the claim is reported as stale rather than silently cleared, silently kept, or silently promoted to done.
3. **Given** a work item with recorded evidence pointers (branch, commit, pull request), **When** the referenced branch is later rebased, squashed, or deleted, **Then** the evidence pointer remains as a historical observation rather than being treated as broken or requiring rewrite (mirroring `docs/WORKTREES.md`'s evidence-immutability rules).

---

### User Story 4 - Materialize a schedulable view for an external coordinator (Priority: P3)

A future Symphony integration (out of scope to build here) needs a materialized view of currently-runnable work items sufficient to dispatch one, without Bindle's own durable model being reshaped around Symphony's tracker schema, and without Bindle duplicating Symphony's own dispatch, retry, or concurrency logic.

**Why this priority**: This scenario is what justifies calling the ledger "pre-scheduling" rather than just "a to-do list" — it's the seam the rest of the coordination pillar (`PLAN.md`, `docs/SYMPHONY.md`) depends on — but it is the lowest priority here because no Symphony adapter code exists yet and none is being built in this feature.

**Independent Test**: Given a ledger with a mix of blocked and unblocked items, generate a projection and confirm it marks exactly the unblocked, unclaimed, non-terminal items as eligible, and that regenerating the projection from the same ledger state twice produces the same result (i.e., the projection is a deterministic, disposable view, not additional durable state).

**Acceptance Scenarios**:

1. **Given** a ledger item that is blocked on an unfinished item, **When** a projection for an external coordinator is generated, **Then** that item is not presented as eligible to run, even if the target coordinator's own adapter would not otherwise check blocking itself.
2. **Given** the same ledger state, **When** a projection is generated twice, **Then** the two projections are equivalent — nothing about generating a projection changes the ledger's own durable state.
3. **Given** no Symphony (or other coordinator) is installed or running, **When** the ledger is inspected, **Then** every user-facing coordination fact (status, blocking, claim, evidence) remains fully available — the ledger is useful with no coordinator present at all.

### Edge Cases

- What happens when a work item's `blocked_by` relationship is circular (A blocks B, B blocks A)? The model MUST make this detectable rather than silently treating both as permanently unavailable or silently ignoring the cycle.
- What happens when two ledger items are promoted from the same underlying spec/plan/task by two different agents unaware of each other? The model MUST make the resulting duplication visible (e.g., both items pointing at the same source) rather than silently merging or silently allowing an ambiguous double-claim on the same underlying work.
- What happens when an item is claimed, and then the spec/plan it was promoted from is later revised or superseded? The item's own status and the source pointer's staleness are independent facts — the model MUST NOT require the ledger to auto-track upstream document revisions, but the source pointer must remain a link an agent can follow to notice the drift.
- What happens when a work item is claimed but its owning agent/session never marks it done, blocked, or released (an abandoned claim with no deleted worktree to detect)? The model MUST make claim staleness inspectable by a human or agent when there is evidence to detect (a deleted worktree/branch), without assuming a background process exists to notice on its own. When there is no such evidence (the worktree still exists, the owner simply stopped), the model explicitly does not claim to detect this automatically — a human applying judgment, using the same explicit release available for a detectably stale claim, remains the only recourse.
- What happens when two agents attempt to claim the very same, still-unclaimed work item at the same instant? The model MUST guarantee that exactly one succeeds and the other receives an unambiguous, immediate "already claimed" result — never a state where both believe they hold it, and never a window where a third party could observe the item as unclaimed while one of the two claims is still being decided.
- Does overriding (releasing) a stale or corrupt claim automatically give the overriding actor ownership of the item? No. Releasing a claim — whether by its owner or by an override justified under FR-019 — only makes the item unclaimed and claimable again; it is not itself a claim, and it is not combined with a subsequent claim into one atomic operation. An actor that wants to hold the item after releasing it MUST separately win a claim attempt through the same arbitration as any other acquisition (the guarantee above), and MUST NOT assume it owns the item until that attempt succeeds — another actor's concurrent attempt may legitimately win instead, in which case the releasing actor holds no claim on the item. The model MUST NOT provide, or be described as providing, an atomic release-and-reacquire ("replace") primitive.
- What happens when the process claiming an item crashes between acquiring the claim and finishing writing its details (owner, timestamp)? The claim MUST still exist and MUST NOT be treated as available — but it also MUST NOT be trusted as a normal, attributable claim; it is surfaced distinctly so a human or agent can resolve it, the same way a stale claim is.
- What happens to a work item's dependency truth once a prerequisite it names in its blocking relationship is completed and later removed from active view (archived)? The model MUST continue to distinguish, forever, between "that prerequisite was satisfied" and "that reference is unknown or corrupted" — a prerequisite's identity and final status MUST remain authoritatively resolvable even after it leaves the active set, and archiving a prerequisite MUST NOT be able to turn a satisfied dependency into an ambiguous one.
- What happens when the repository has multiple linked worktrees on different branches at the time reconciliation runs? Reconciliation MUST be able to observe work-item claims and evidence regardless of which worktree it is invoked from, consistent with `docs/WORKTREES.md`'s repository-identity model (the Git common directory), not the invoking worktree.
- What happens when a work item is superseded rather than completed? The model MUST retain a pointer from the superseded item to whatever superseded it (mirroring `docs/DECISIONS.md`'s own "superseded in place, never edited away" convention), rather than deleting the record.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The model MUST give every work item a stable identifier that remains valid independent of the agent session, worktree, or branch that created it.
- **FR-002**: The model MUST record, for every work item, a pointer back to the upstream intent artifact it was promoted from (a Spec Kit task, a plan section under `plans/`, or an explicitly recorded ad hoc origin) — the ledger MUST NOT be the only record of *why* the work exists.
- **FR-003**: Creating a work item MUST be an explicit, deliberate act performed by an agent or maintainer. Generating or editing an upstream intent artifact (e.g., running `/speckit.tasks`) MUST NOT, by itself, create or modify any durable work item.
- **FR-004**: The model MUST represent a work item's coordination state as a small number of independent (orthogonal) facts — at minimum: a coarse status, a blocking relationship, an ownership/claim, and zero or more evidence pointers — rather than as one large enumerated lifecycle covering every combination of these facts.
- **FR-005**: The coarse status vocabulary MUST distinguish at least: work that is not yet finished ("open"), work that is finished ("done"), and work that has been explicitly withdrawn or replaced ("superseded") without being deleted. The model MUST NOT require a richer status vocabulary than this to represent claiming, blocking, or partial progress — those are separate facts (FR-006–FR-008), not additional status values.
- **FR-006**: The model MUST allow a work item to declare that it is blocked on zero or more other work items by identifier, and MUST allow computing, from that declaration plus each referenced item's status, whether the item is currently blocked — without requiring the model to compute or expose any dispatch order, priority, or ranking among unblocked items. This declared set of blocking identifiers is retained as originally recorded; the model MUST NOT require it to be edited or pruned when a referenced item later resolves — "is this item currently blocked" is always answered fresh, not by keeping the declared set itself in sync.
- **FR-007**: The model MUST allow a work item to be claimed by an identified owner (an agent, session, or person) at a point in time, optionally together with a pointer to the worktree or branch the claim is being worked in. A claim MAY be released by its owner at any time, or — only when justified by evidence that the claim is stale or unattributable (FR-019) — by another actor performing an explicit override. Retaining a record that an item was previously claimed, once released, is optional, not guaranteed.
- **FR-008**: The model MUST allow zero or more evidence pointers to be attached to a work item (e.g., a branch name, a commit or commit range, a pull request or issue reference) as the work progresses, without requiring the model to duplicate the content those pointers refer to.
- **FR-009**: The model MUST make it possible to determine, from repository state alone (without a live coordinating process and without asking the agent or session that made a claim), whether a given claim's recorded worktree or branch still exists, and whether a claim's own record is intact and readable — the model MUST NOT require trusting a stale or unreadable claim as still active and attributable.
- **FR-010**: The model MUST support reconciliation as a read-only operation: comparing recorded work-item state against observed repository state (branches, worktrees, commits, and — when available — pull requests) and reporting drift, without silently mutating a work item's status, claim, or blocking facts as a side effect of reconciling. Finding a claim stale or corrupt MUST NOT, by itself, change whether the item is computed as available — a stale or corrupt claim continues to make the item unavailable until explicitly released (FR-019).
- **FR-011**: The model MUST remain intelligible and usable when read from any linked worktree of the repository, not only the worktree in which a given item was created or claimed, consistent with this repository's Git-common-directory identity model.
- **FR-012**: The model MUST NOT depend on any particular external work coordinator (Symphony or otherwise) being installed, configured, or running in order for an agent to create items, read items, determine availability, record claims, or record evidence.
- **FR-013**: The model MUST define what a future external coordinator projection needs to be generated *from* it (at minimum: an identifier, a coarse active/terminal classification, and a computed eligibility fact reflecting blocking), without adopting any specific coordinator's own field names, states, or schema as the ledger's own model.
- **FR-014**: A projection generated for an external coordinator MUST be derivable purely from the ledger's own durable state at the time of generation (i.e., regenerable on demand), and MUST NOT become a second durable store that the ledger itself depends on or falls out of sync with.
- **FR-015**: The model MUST NOT require or assume that dependency/blocking relationships form a scheduling priority order, retry policy, or concurrency limit — those remain the responsibility of whatever executes the work (a human, or a future coordinator), not of this ledger.
- **FR-016**: The model MUST allow a superseded work item to retain a pointer to whatever superseded or replaced it, rather than being deleted outright, mirroring this repository's existing decision-record convention of superseding in place.
- **FR-017**: The model MUST treat long-term historical narrative about *why* work happened (design rationale, accepted decisions, retrospectives) as continuing to live in this repository's existing durable documentation (`docs/DECISIONS.md`, `plans/`) rather than being reproduced inside the ledger — the ledger records *coordination facts about currently or recently pending work*, not a permanent history of all work ever done.
- **FR-018**: The model MUST guarantee that, when multiple attempts to claim the same currently-unclaimed work item happen concurrently, exactly one attempt succeeds and every other attempt receives an unambiguous, immediate failure result — never a state where two claims are both recorded as having succeeded for the same item, and never a window in which the item could be observed as unclaimed by a third party while one attempt's outcome is still undetermined.
- **FR-019**: An override release of a claim (one performed by someone other than its recorded owner) MUST only be treated as legitimate when justified by observed evidence that the claim is stale (its recorded worktree or branch no longer exists) or corrupt (its record exists but is unreadable) — never performed automatically, on a timer, or without that evidence having been surfaced first.
- **FR-020**: The model MUST keep every work item's declared blocking relationship resolvable to an unambiguous outcome — satisfied, still open, or genuinely unresolvable — even after a named prerequisite item has been archived out of the active set. Archiving a prerequisite MUST NOT be able to turn a previously-satisfied dependency into an unresolvable one, and MUST NOT require refusing or deferring the archival itself to keep that guarantee.
- **FR-021**: A blocking relationship that cannot be resolved against either an active work item or a retained record of an archived one (a genuinely dangling reference) MUST be treated as still blocking, never as satisfied, and MUST be surfaced for explicit correction rather than silently ignored.

### Key Entities *(include if feature involves data)*

- **Work Item**: One decomposed, independently claimable unit of implementation work. Carries a stable identifier, a short human-readable summary, a source pointer (to the spec/plan/task it was promoted from), a coarse status (open / done / superseded), a set of blocking references to other work items, an optional current claim, and zero or more evidence pointers. Superseded items retain a pointer to their replacement.
- **Claim**: A record that a specific owner (agent, session, or person) has taken responsibility for a work item as of a point in time, optionally together with a pointer to the worktree or branch the claim is being worked in. Tracked independently of the work item's other facts specifically so that concurrent claim attempts on the same item can be arbitrated unambiguously — exactly one succeeds, every other attempt fails immediately and unambiguously (FR-018). A claim can be released by its owner, or, when reconciliation evidence justifies it, released by another actor as an explicit override (FR-019). A claim is not itself a status value — an item can be open-and-unclaimed or open-and-claimed.
- **Blocking Reference**: A directed relationship from one work item to another, meaning the first cannot be considered eligible to start until the second reaches a terminal status (done or superseded). Blocking references are declared once and retained as originally recorded; whether one is *currently* satisfied is always determined fresh, by resolving the referenced item's status (directly, or via its Tombstone if archived), never by editing the declaration itself. Blocking references are coordination facts an agent, a human, or a future projection can read; they are not themselves a scheduling priority or dispatch order.
- **Evidence Pointer**: A reference to observed, provider-owned implementation state relevant to a work item — a branch name, a commit or commit range, a pull request, or a similar identifier — held as a pointer rather than a copy, consistent with this repository's existing replaceability rule for evidence.
- **Source Reference**: A pointer from a work item back to the upstream intent artifact that justified its existence (a Spec Kit feature/task identifier, a plan file and section, or an explicitly recorded ad hoc origin). Distinct from a Claim or Evidence Pointer: it explains *why* the item exists, not who is doing it or what has been produced so far.
- **Tombstone**: The minimal, permanent record left behind when a work item is archived out of the active set — just enough (its identifier, its final done/superseded status, and what superseded it, if applicable) to keep any other item's blocking relationship to it resolvable forever, without retaining the rest of the archived item's content. Distinct from a durable historical record: a Tombstone exists only to answer "was this dependency satisfied," not to preserve why the work happened (FR-017, FR-020).
- **Reconciliation Report**: The read-only output of comparing recorded work-item state (claims, evidence, blocking) against currently observed repository state (worktrees, branches, commits, pull requests where available), surfacing drift — such as a stale or corrupt claim, a dangling blocking reference, or evidence pointing at a deleted branch — without itself mutating the ledger.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A new agent session, in a worktree different from the one that created them, can enumerate the complete and correct set of currently-available work items (not claimed, not blocked, not done, not superseded) using only repository state — with zero information carried over from the session or process that created those items.
- **SC-002**: In constructed test scenarios covering chains of three or more blocking relationships, the set of items correctly excluded from "available to start" matches the expected set in 100% of cases.
- **SC-003**: In constructed test scenarios where a claimed item's recorded worktree or branch has been deleted, reconciliation correctly reports that claim as stale in 100% of cases, and never reports the item as done solely because its worktree disappeared; the item remains computed as unavailable until an explicit release is performed.
- **SC-004**: Two concurrently claimed, independent work items can each be updated (claim, evidence, status) without either update overwriting, corrupting, or silently discarding the other item's record, verified across repeated concurrent-update scenarios.
- **SC-004a**: In repeated test scenarios where two or more concurrent attempts target the *same* currently-unclaimed work item, exactly one attempt succeeds every time and every other attempt receives an immediate, unambiguous failure — 100% of trials, with zero trials producing two recorded successful claims for the same item.
- **SC-005**: Regenerating a coordinator-facing projection twice from the same, unchanged ledger state produces an equivalent projection both times, confirming the projection is a derived view and not a second source of truth.
- **SC-006**: No requirement in this specification requires computing a dispatch order, retry count, or concurrency limit among available work items — confirmed by review, since introducing any would indicate scope drift into building a scheduler.
- **SC-007**: An agent or maintainer can determine, without reading Symphony's (or any other coordinator's) own source code or configuration, what a work item minimally needs to carry in order to eventually be projected for that coordinator — confirmed by this specification's own Key Entities and FR-013 being sufficient reference on their own.
- **SC-008**: In constructed test scenarios where a prerequisite item is completed and then archived, every dependent item's blocking evaluation still correctly reports that prerequisite as satisfied in 100% of cases — archival never causes a previously-satisfied dependency to be reported as unresolved or unknown.
- **SC-009**: In constructed test scenarios containing a `blocked_by` reference to an identifier that never corresponded to any real item, that reference is reported as unresolvable (never as satisfied) in 100% of cases, and is distinguishable, in the reported detail, from a reference to an item that was genuinely completed and archived.
- **SC-010**: In constructed test scenarios where a claim acquisition is interrupted after its claim record is created but before its details (owner, timestamp) are fully written, reconciliation reports that claim as corrupt — distinguishable from a stale claim — in 100% of cases, and the item remains computed as unavailable until an explicit release is performed.

## Assumptions

- The ledger's durable representation is repository-local, untracked, machine-local coordination state — resolved from the repository's Git common directory (`docs/WORKTREES.md`: "a local repository identity shared by linked worktrees," whose "absolute path is machine-local and must not be treated as a portable cross-machine identifier"), not a Git-tracked file. It does not participate in `git diff`, merge, or pull-request review, and Git is not the mechanism by which it durably survives — it durably survives the same way Projectmem's (D022/D033) and QMD's (D036) own repository-scoped state already does: by living outside the working tree Git tracks at all. "Repository-local" means scoped to one repository clone's Git common directory on one machine: every linked worktree of that same clone resolves the identical ledger location and observes the identical state, so the ledger survives an individual agent session ending, a worktree being created or removed, and a branch checkout changing underneath it — but it is not transported by `git push`/`git pull`/`git clone`/`git fetch`, is not visible to a second clone of the same repository (a different machine, or a second independent checkout on this one), and is not merged or code-reviewed the way this repository's Git-tracked intent and history are. Git remains the substrate for durable *intent* (the Spec Kit tasks and plans a work item's Source Reference points back to, FR-002) and for durable *history* once work completes (`docs/DECISIONS.md`, `plans/`); the ledger itself is *coordination* state about that intent's current, in-flight execution, deliberately kept outside Git's own tracked-and-merged workflow rather than reusing it as a coordination database. The exact file format and on-disk layout remain deferred to the planning phase — only this tracked-vs-machine-local boundary, and what durability across sessions/worktrees does and does not imply, is settled by this specification.
- A work item is created only by explicit promotion from an upstream intent source; this specification does not assume or require automatic decomposition of a spec, plan, or task list into work items.
- A future external coordinator (Symphony, or any replacement) is expected to consume a generated, disposable projection of this ledger, not to read or write the ledger's own durable files directly — this specification does not decide how that projection is delivered (a generated file, a command's output, or another mechanism).
- Claim arbitration between two agents attempting to claim the very same, currently-unclaimed work item at the very same instant is **in scope and resolved** (FR-018/FR-019, SC-004a): exactly one succeeds and the other fails immediately and unambiguously, using a mechanism no live coordinating process is required to mediate. What remains out of scope is claiming *multiple different* work items as a single all-or-nothing transaction, and any coordination granularity finer than one item's own claim decision — those, when they matter, remain the responsibility of whatever is actively dispatching work in a single run (a human, or a future coordinator), not of this durable model.
- A work item that reaches "done" or "superseded" is expected to be archived out of active view once it has been reconciled, leaving behind only a minimal, permanent record of its final status (FR-020) — not the rest of its content, and not retained indefinitely as a growing historical log. This specification's ledger is scoped to currently and recently pending work plus the small permanent fact needed to keep other items' dependencies resolvable, not to becoming a permanent project history (that role continues to belong to `docs/DECISIONS.md`, `plans/`, and Git itself).
- This specification does not require, assume, or preclude a specific number of work items, agents, or worktrees; scenarios above use small numbers only to keep acceptance testable, not to imply a scale ceiling.
