## Decision: ownership — who owns the durable coordination facts?

**Decision**: Bindle owns the ledger's format and store, as a new, explicitly bounded kind of Bindle-owned state — **coordination state for currently/recently pending decomposed work** — distinct from the "user history" `docs/PHILOSOPHY.md` forbids Bindle from owning, and distinct from "working reasoning" (projectmem's own domain).

**Rationale**: The three-question admission screen (`AGENTS.md`, "Architecture rules"; `docs/PHILOSOPHY.md`, "Feature admission test") was applied to every plausible alternative owner before concluding this:

- **Git alone**: rejected by the task's own explicit constraint and by evidence — commits/branches encode *what happened*, not *what is currently blocked, claimed, or available*. `docs/WORKTREES.md`'s own "History scenarios" table treats branch/commit facts as historical observations, not live coordination state; nothing in Git represents "item X is currently claimed by agent Y."
- **GitHub Issues/PRs**: rejected — `AGENTS.md` ("Planning") explicitly states "Do not require GitHub Issues," and this ledger must work fully offline and across worktrees without a network round-trip (`docs/SCOPE.md`'s "Bindle does not own... GitHub issue tracking"). GitHub remains a valid *evidence pointer* target (a PR number an item can reference), never the required substrate.
- **Projectmem**: rejected as the *owner*, not merely deprioritized — projectmem's own domain is append-only working reasoning (issues/attempts/fixes/decisions) about *why* something happened, and it is explicitly branch-blind (`docs/DATA-OWNERSHIP.md`, "Trust boundary" note: "events carry only a HEAD SHA — no branch, no worktree, no rewrite handling"). The ledger's job is close to the opposite: current, mutable, worktree/branch-aware coordination facts (claimed-by-whom-in-which-worktree, blocked-on-what) that must stay accurate as of *now*, not an append-only log of *what an agent believed happened*. `docs/PHILOSOPHY.md`'s own rejection example ("Re-implement repository memory because projectmem is branch-blind... an imperfect integration does not justify duplication") does not apply here, because this is not a re-implementation of projectmem's own domain — it is a different domain projectmem was never designed to hold.
- **Symphony's own tracker** (`.symphony/local_tracker.json`, confirmed this session at the pinned fork revision): rejected as the *source of truth*, though it is exactly right as the *target of a generated projection*. Symphony's own `Tracker` behaviour (`elixir/lib/symphony_elixir/tracker.ex`) has no write/claim/update callback beyond `set_issue_state/3`, no `dispatchable` field for the `local` adapter (hardcoded `true` — see "Decision: projection contract" below), and its shape is Symphony's own adapter concern, swappable for Linear/GitHub/Jira/Asana/GitLab per Symphony's own `SPEC.md`. Coupling Bindle's durable model 1:1 to one adapter's JSON shape would violate D014 (replaceability) the moment Symphony is replaced or a different tracker adapter is selected, and would let an external tool's format decide Bindle's own ontology — exactly what the task's own brief forbids ("Symphony does not become the authoritative ontology for Bindle's work").
- **A new Bindle-owned store**: the only remaining candidate, and the one the task's own framing anticipates ("Determine what the durable implementation-work record actually is... Who naturally owns it?"). This passes `docs/PHILOSOPHY.md`'s nine-criteria test: it bridges intent (Spec Kit/plans) and execution (a future coordinator) — a real, previously-unbridged seam (criterion 1); it operates through Bindle's own supported read/write functions on its own store, no other tool's private store (criterion 2); its output *toward* a coordinator is a disposable, regenerable projection (criterion 3); it does not become the sole owner of user history (criterion 4 — see below); it stays useful if Symphony is replaced by a different coordinator, since the projection step is the only coordinator-specific part (criterion 5); it solves an observed, named repeated need (surviving session/context loss across concurrent agent work), not hypothetical scope (criterion 6); it cannot be handled by a routing rule or small script alone — the underlying facts (claim, blocking) do not yet exist anywhere to route (criterion 7); it is explicitly designed around the Git-common-directory identity model (criterion 8, `docs/WORKTREES.md`); and it does not preserve completed items forever merely because preservation is possible — see "Decision: retention" below (criterion 9).

This decision is unaffected by the persistence-format correction below: nothing about choosing SQLite over plain files changes *who* owns the ledger, only what it is physically stored as.

**Philosophy-and-scope implication, stated plainly rather than routed around**: `docs/PHILOSOPHY.md`'s current "Bindle-owned runtime state" language ("configuration, disposable cache, and explicit export") and `docs/DATA-OWNERSHIP.md`'s ownership table do not yet have a row for this shape of state. This is not a request to relax D014–D016; it is a request to **add** an explicit, narrow acknowledgment that bounded, non-derivable, working *coordination* state (parallel to projectmem's own "working notes — not truth" bucket, but Bindle-owned because no adoptable third party covers this domain) is a distinct, admissible fourth category, provided it stays: (a) bounded to currently/recently pending work, never a permanent log; (b) never the only record of *why* work exists (that stays with Spec Kit/plans, FR-002/FR-017); and (c) never the only record of *that* work happened once it completes (that promotes to `docs/DECISIONS.md`/`plans/`/Git, same as today). This is a recommendation for a future `docs/DECISIONS.md` entry to make explicitly at adoption time, not a change this specification-only feature makes unilaterally — see the final report accompanying this revision for why this remains open rather than closed now.

**Alternatives considered**: A generic Bindle "Component/Provider" abstraction spanning guardrails/projectmem/skills/QMD/ledger — rejected outright per D033's and D035's own closing precedent ("two kits were enough to reveal real structural differences... a third, differently-shaped kit is the point at which to revisit," never triggered since each seam so far has stayed genuinely different-shaped). A generic ORM or persistence-abstraction layer wrapping SQLite (e.g. SQLAlchemy) — rejected for the same reason, applied to the new format: one purpose-built module using `sqlite3` (stdlib) directly, exactly like `projectmem.py`/`qmd.py` use their own respective native tools directly, not a generic data-access framework introduced speculatively.

## Decision: storage location — where does the ledger live?

**Decision**: The ledger's file is resolved from the repository's Git common directory (`RepoInfo.repo_root`/`git_common_dir` in `src/bindle/repo.py`), **not** the invoking worktree root — e.g., conceptually `<repo_root>/.bindle-work/ledger.sqlite3` (final path/name is an implementation-slice detail, not fixed by this plan). This decision is unchanged in substance by the persistence-format correction below — only the illustrative path now names a single database file instead of a directory of per-item files.

**Rationale**: This exactly mirrors the correction D033 already made for Projectmem's own hook installation (`cwd=repo_root`, not `worktree_root`, because a linked worktree's `.git` is a *file*, not a directory) and matches `docs/WORKTREES.md`'s repository-identity rule directly: "The Git common directory is a local repository identity shared by linked worktrees." A ledger scoped to `git_common_dir` is visible and consistent from every linked worktree on this machine without any synchronization step, satisfying spec.md's FR-011 and User Story 3 (two worktrees, two claims, no interference) by construction — two worktrees open the same physical SQLite file.

**Alternatives considered**:
- *Worktree-local storage* (like the skill kits' Codex materialization, D035): rejected — explicitly ruled out by the task's own brief ("Do not assume worktree-local state is sufficient... Work items should remain intelligible if a worktree disappears"), and it would mean two worktrees literally cannot see each other's claims, defeating User Story 3 outright. This reasoning does not depend on file format, and is unchanged by the SQLite decision — a worktree-local SQLite file would have exactly the same defect as a worktree-local TOML directory.
- *Tracked, git-committed database following the checked-out branch* (like `bindle.toml`, `specs/`): considered seriously, then rejected for the ledger's *in-flight* coordination facts specifically, for the same reasons the original decision rejected a tracked TOML layout — a tracked-per-branch database file only becomes visible to another worktree once its owning branch is merged, would turn ordinary claim/status churn into commit noise, and would turn merges into a source of unrelated binary-file conflicts (worse than text-file conflicts, since SQLite files are not line-mergeable at all). This is the same shape of problem Projectmem (D022) and QMD (D036) already solved by choosing repository-scoped, untracked, machine-local storage instead of tracking their own state — this plan follows that now twice-established precedent rather than inventing a third pattern, regardless of the file format chosen underneath it.

## Decision: storage format — SQLite, superseding the original plain-file design

**Decision**: A single, small SQLite database file (not one file per work item, not a directory of claim/tombstone files) is the ledger's persistence mechanism. The conceptual relational schema — tables for work items, `blocked_by` edges, claims, and evidence pointers — is specified in `data-model.md`.

**This decision supersedes** this document's original "Decision: storage format," which chose one plain-text TOML file per work item plus separate, atomically-created claim files and tombstone files, and was accepted as part of this specification's first draft (merged via PR #26). The override is intentional and directed, not a re-opened evaluation — see "Rationale for the override" below — and the original decision's full text is preserved, unedited, under "Superseded decision, preserved for history" at the end of this section, per this repository's own decision-history convention of superseding in place rather than rewriting history (`docs/DECISIONS.md`'s governing line, applied here even though this file is not itself `docs/DECISIONS.md`).

**Rationale for the override**, recorded plainly:

- **Direct SQL queryability and ad hoc inspection are desired capabilities, not merely tolerated ones.** The original decision optimized for "readable with `cat`/a text editor even if `bindle` itself is broken." That property is still available under SQLite (`sqlite3 <path> "SELECT ...`" is exactly as available without `bindle` running as `cat` was), but the newly clarified requirement goes further: the ledger should be *queryable* — joins across work items, blocking edges, and claims; ad hoc filtering during development and operation — which a directory of independent small files cannot offer without re-deriving a query engine in application code.
- **Work-item mutations that touch multiple related facts need straightforward transactional atomicity.** The original design solved this piecemeal and per-mutation-type: exclusive file creation for claims, "archival and tombstoning happen together" as an informally-atomic two-artifact operation, temp-then-rename for item files. Each of those was a separately-reasoned, bespoke atomicity argument. A relational database gives one uniform mechanism — a transaction — for every mutation that touches more than one fact, including ones the original design never fully closed (e.g., releasing a stale claim and recording an Evidence Pointer noting the override, as two coupled writes).
- **Claims, dependency changes, state transitions, and archival should not each require their own filesystem atomicity protocol.** The original design already required three conceptually distinct protocols (exclusive create for claims, temp-then-rename for item mutations, atomic dual-write for archival+tombstoning). That proliferation of one-off protocols is itself a complexity cost the original decision's own "keep it boring" framing did not fully account for — SQLite's transaction support collapses all of them into the same primitive.
- **SQLite is an acceptable, well-understood local dependency; avoiding it is not itself a meaningful simplicity objective for Bindle.** `sqlite3` is Python stdlib, exactly as the original decision already noted — the original rejection was never actually about dependency weight, it was about format properties, and those properties are now judged differently (below) now that queryability and multi-fact transactions are explicit, named goals rather than implicit non-goals.
- **The concern that motivated rejecting one-shared-file designs (write contention between unrelated items) does not carry over to SQLite the way it does to a single shared JSON/YAML document.** The original decision's strongest argument against a single shared file was write contention between *unrelated* items (SC-004). That argument was specifically about a naive whole-document read-modify-write pattern (the shape Symphony's own `local_tracker.json` and the retired `feat/local-orchestration` branch both used) — it is not an argument against a relational database, which is designed exactly to give independent, transactionally-isolated row-level writes to unrelated records without the caller re-deriving that guarantee. Rejecting SQLite in the original decision by analogy to "one shared file" conflated the two.
- **We specifically do not want the implementation to evolve into application-managed manipulation of many local state files.** The original design already needed three file *kinds* (item files, claim files, tombstone files) coordinated by hand-rolled, per-kind atomicity rules, and each future mutation type (e.g., a richer reconciliation record, a future claim-history table) would have needed its own new file kind and its own new atomicity argument. SQLite absorbs that growth inside one engine's own well-tested transaction and constraint machinery instead of Bindle re-deriving file coordination primitives repeatedly.
- **SQLite still satisfies every architectural constraint the original decision was itself protecting**: local (a single file, no server process), durable (survives process/session end), offline-capable (no network dependency, matching FR-012), inspectable (`sqlite3` CLI or any SQLite GUI, arguably a *stronger* inspection story than a directory of TOML files once more than a handful of items exist and cross-item queries are wanted), portable (a single file copies/backs up trivially), and introduces no hosted service or control plane (no daemon, matching `AGENTS.md`'s "On when in use" posture). Nothing about the admission screen in "Decision: ownership" above changes.

**Why this override happens now, before any implementation exists**: this is the correct time to make this change — no `src/bindle/work_ledger.py` or `tests/test_work_ledger.py` exists yet (per `plan.md`'s Project Structure, both are explicitly still future work), so there is no implementation to migrate off the superseded design, only specification and planning artifacts to correct. Overriding the decision now, before a slice is built against the wrong persistence mechanism, is strictly cheaper than overriding it after.

**Superseded decision, preserved for history** (accepted 2026-08-26, merged via PR #26, superseded by this revision the same day once the desired properties above were clarified):

> **Decision**: One plain-text file per work item (TOML, matching `bindle.toml`'s own precedent and this project's existing stdlib-only `tomllib` reading pattern from `src/bindle/skills/config.py`), not a single SQLite database.
>
> **Rationale**, evaluated directly against `docs/SCOPE.md`'s and `docs/PHILOSOPHY.md`'s own stated requirements for Bindle-owned state:
>
> - **Dependency weight is a non-argument either way.** `sqlite3` is Python stdlib, exactly like `tomllib` — this decision is not "avoid a dependency," it is about format properties.
> - **Scale does not justify a database.** This ledger targets a handful to a few dozen concurrently-relevant items per repository (spec.md's own Assumptions: "does not... imply a scale ceiling," but every acceptance scenario is sized in single digits). At this scale, `rg`/directory listing/stdlib parsing are sufficient, mirroring this repository's own governing precedent for *not* reaching for heavier tooling before demonstrated need (`AGENTS.md`, "Code intelligence": "prefer... rg, fd, Git, and language tooling" before an adopted heavier tool; D020/D021's evaluate-before-adopt bar).
> - **Inspectability and recovery.** `docs/SCOPE.md`'s own storage criteria list "simple inspection/recovery" and "no hidden irreplaceable history owned only by Bindle" as explicit tests. A directory of small text files can be read, diffed, hand-edited, and recovered with `cat`/a text editor even if `bindle` itself is broken or absent; a SQLite file cannot, without the `sqlite3` CLI or matching schema knowledge — a materially higher recovery bar for content this plan wants to keep genuinely inspectable.
> - **One file per item, not one file for all items.** Rejected the alternative of a single JSON/TOML document holding every item (the shape Symphony's own `local_tracker.json` uses, and the shape the prior `feat/local-orchestration` branch's SQLite table effectively serialized to a single database file). A single shared file means every concurrent writer — even to unrelated items — contends on the same file, the opposite of spec.md's SC-004 ("two concurrently claimed, independent work items can each be updated... without either update overwriting... the other item's record"). Independent files give independent items true write independence, using the filesystem's own existing atomicity primitives (e.g., write-to-temp-then-rename) rather than requiring a transaction manager.
> - **A directory of files still has directory-level races**, but they are cheap and standard to guard (an item-creation race is a create-if-absent check on one small file, not a schema migration or a locked table) — no `sqlite3` transaction semantics are needed, because deliberately, per spec.md's own Assumptions, this plan does not attempt sub-second in-process claim arbitration.
> - **External precedent, not proof but corroborating signal**: Symphony's own shipped local tracker (`local/init.ex`, `local/store.ex`, confirmed this session at the pinned fork revision) chose a plain JSON file over SQLite for its own, structurally similar problem (a small number of tracked issues, one process, simple inspection). D037 already recorded this correction to the exploration plan's earlier, unverified SQLite assumption. This plan's own conclusion is independently derived from this repository's storage criteria, not copied from Symphony's choice — but the fact that a comparable system converged on the same answer is worth recording as corroboration.
>
> **Alternatives considered**: SQLite (rejected, above); a single JSON Lines append log (rejected — an append-only log fits an event history, not current mutable state per item, and would need periodic compaction to answer "what is item X's current status" without replaying the whole log); a single YAML/JSON document with one entry per item, à la `local_tracker.json` (rejected for the write-independence reason above).

This history matters for a future reader: the "one file per item" reasoning above was not wrong given the goals it was optimizing for (minimal dependency footprint, maximal `cat`-level inspectability, no query capability assumed to be wanted). What changed is the goal set itself — SQL queryability and uniform multi-fact transactional atomicity are now explicit, named requirements — not a discovery that the original reasoning contained an error.

## Decision: retention — completed work is thinned in place, not tombstoned in a separate artifact

**Decision**: A work item reaching `done` or `superseded` is **archived in place, within a single database transaction**, once reconciled. Archiving an item does not delete its row or move it to a second table; it clears (sets `NULL`) every column that is not needed to keep dependency resolution and supersession-chain-following correct forever (`title`, `source_kind`, `source_locator`, `source_promoted_by`, `created_at`), sets `archived_at` to the archival timestamp, and — in the same transaction — deletes that item's own `blocked_by` edges (the dependencies *it* declared, not edges other items declare against it), its evidence pointers, and any lingering claim row. `id`, `status`, and `superseded_by` are never cleared; see `data-model.md`'s "Archival" section for the exact column-level contract. "Reconciled" retains its original meaning: Bindle's own reconciliation-against-repository-state (claim, evidence, and blocking drift), never satisfied by, or waiting on, an external coordinator generating a projection. Completion remains authoritative the moment `status` changes to `done`/`superseded`; archival (the thinning transaction) proceeds on Bindle's own timing after that, independent of whether a coordinator projection ever observed the terminal state first (unchanged from the original decision — see `contracts/coordinator-projection.md`, "What the projection explicitly does not do").

**This decision supersedes the mechanism, not the behavior, of the original "Decision: retention."** The original decision's *behavioral* commitment — the full record (title, source, evidence, claim history) is discarded at archival; a small permanent fact survives forever specifically to keep dependency resolution unambiguous; archiving and making that fact durable happen as one indivisible step — is preserved exactly, per this correction's own brief ("preserve the valid domain and behavioral work in 001"). What changes is that the original decision needed a **second artifact type** (a three-field Tombstone file, distinct from the Work Item file it replaced) specifically because a plain-file model has no way to "shrink a record in place" other than deleting it and writing something smaller elsewhere. SQLite does not have that limitation: `UPDATE work_items SET title = NULL, ... WHERE id = ?` shrinks the *same row* in place, inside the *same table*, in the *same transaction* that also deletes the row's evidence and edges. **This is a genuine simplification SQLite enables, not a mechanical translation of the old two-artifact design** — per this correction's own instruction not to reproduce the old Tombstone mechanism merely because SQLite could technically host an equivalent second table. A second `tombstones` table (mirroring the old file-based active/tombstone split) was considered and rejected below specifically because it would reintroduce the same two-artifact-type complexity SQLite exists to remove.

**Rationale**: `docs/PHILOSOPHY.md`'s preservation rule (D016) and criterion 9 of the feature admission test ("does not preserve information merely because preservation is possible") still govern, exactly as in the original decision — nothing about persistence mechanism changes *whether* full detail should be discarded at archival, only *how*. Keeping the archived item as a thinned row in the same `work_items` table, rather than a separate `tombstones` table, also directly simplifies the next decision below (dependency resolution across archival no longer needs a two-set lookup — see there for why).

**One narrow, deliberate expansion beyond the original three-field Tombstone**: this decision retains one additional column after archival that the original Tombstone did not carry — `archived_at`, an operational timestamp recording when the thinning transaction ran. This is a single scalar fact (not narrative, not evidence, not growing), added because it is operationally useful (distinguishing "recently archived" from "archived long ago" without inference) and because, unlike the original file-based design, there is no separate "Tombstone was created" event to infer this from — a thinned row's own `archived_at` column is the only place this fact could live. This is called out explicitly, per this correction's brief, as a narrowly scoped adjustment rather than left implicit.

**Alternatives considered**:
- *A separate `tombstones` table, populated by a trigger or application code when an item reaches a terminal status* (the direct relational mirror of the old file-based active/tombstone split): rejected — this would require dependency resolution to still perform a two-table lookup (active row, then tombstone row) exactly as the file-based design did, forfeiting the simplification a single always-present, sometimes-thinned row provides, for no additional correctness benefit. This is exactly the "mechanical translation of the old tombstone-file mechanism" this correction's own brief warns against.
- *Retain full-detail rows forever, with an `archived` boolean flag only hiding them from default listings*: rejected — this reintroduces exactly what D016/criterion 9 forbid: preserving evidence pointers, claim history, and source detail indefinitely merely because a database makes that easy, turning the ledger into a permanent task-history database (FR-017's own prohibition), which remains this repository's job for `docs/DECISIONS.md`/`plans/`/Git, not the ledger's.
- *A hard `DELETE` of the row once terminal, keeping no trace at all*: rejected, unchanged from the original decision's own reasoning — this reopens exactly the dependency-resolution ambiguity ("was this dependency satisfied, or was the reference always invalid?") the next decision exists to close.

## Decision: dependency resolution across archival — a single-table lookup replaces the two-set lookup

**Problem** (unchanged from the original decision, restated for context): if B is `blocked_by` A, A becomes `done`, and A is later archived, evaluating B's blocked status later needs an authoritative answer that distinguishes "A finished and was archived" (fine — satisfied) from "A was never a valid id, or its record was lost" (a real problem — must stay conservatively blocking).

**Decision**: Because archival (above) thins a row in place rather than removing it from `work_items` entirely, resolving a `blocked_by` entry is now **always a single lookup against one table**, never a two-step active-then-tombstone resolution: `SELECT status, superseded_by FROM work_items WHERE id = ?`. If a row is returned, its `status` governs directly — `open` → still blocking; `done` or `superseded` → satisfied — regardless of whether that row is currently active or has been thinned by archival, because `status` and `superseded_by` are exactly the two columns archival guarantees are never cleared. If no row is returned at all, the reference is `dangling_blocker` — genuinely unresolvable, kept conservatively "still blocking," and surfaced for correction. A missing row can now only ever mean "this id was never a valid work item" (a write-time mistake, or corruption — see below), because a work item that genuinely existed and finished is never actually removed from `work_items`, only thinned; the two cases the original problem asked to keep apart remain kept apart, now by the schema's own retention guarantee rather than by a second artifact.

**A foreign key constraint enforces this at write time, not only at read time.** `work_item_blocked_by.blocked_on_id` is declared `REFERENCES work_items(id)`, enforced whenever a connection has `PRAGMA foreign_keys = ON` (a mandatory per-connection setting — see the new "Decision: connection lifecycle" below). This means that, in the normal write path, a `blocked_by` edge naming a nonexistent id is **rejected immediately at declaration time** with a constraint-violation error — a stronger, earlier form of "surfaced for explicit correction" than the original file-based design could offer, where a dangling reference could only ever be *discovered later* by reconciliation. Because `work_items` rows are never hard-deleted (only thinned by archival, which never removes the row), the foreign key relationship is never invalidated by an item's own lifecycle — an edge that validly referenced an item at creation time continues to validly reference that same row, thinned or not, forever.

**`dangling_blocker` remains a defined reconciliation finding, as a defense-in-depth check, not the primary integrity mechanism.** A dangling edge can still exist in practice if: (a) a connection ran with `PRAGMA foreign_keys` left at SQLite's off-by-default state (an operational mistake — see "Decision: connection lifecycle"), or (b) the database file was modified outside Bindle's own write path (a generic SQL client, manual editing, or file-level corruption) in a way that bypassed the constraint. Reconciliation's `LEFT JOIN work_item_blocked_by TO work_items` check (see `data-model.md`) catches either case and reports `dangling_blocker` exactly as before — the finding's *meaning* (a reference that cannot be resolved, must stay conservatively blocking, must be surfaced) is unchanged from the original decision; only its expected *frequency* changes, from "a normal, if unwanted, outcome of an ordinary typo" to "a signal that something bypassed the ledger's own write-path guarantees."

**Case-by-case outcomes** (all computed, never stored, via the single-table lookup above):
- Dependency still open (`status = 'open'`) → still blocking.
- Dependency satisfied (`status = 'done'`) → satisfied, whether the row is active or archived-and-thinned.
- Dependency superseded (`status = 'superseded'`) → satisfied — unchanged from the original rule; the named work will not appear under that identity, and re-pointing to a replacement, if the dependency still matters, is an explicit act.
- Referenced id resolves to no row at all → `dangling_blocker`, treated as still blocking (conservative default — never silently promoted to satisfied) and surfaced by reconciliation; in the normal write path this is prevented outright by the foreign key constraint, so its practical occurrence is now a corruption/misconfiguration signal rather than an expected outcome of ordinary use.

**Indirect cycles** (`A blocked_by B`, `B blocked_by A`, via two independently-written edges) remain a *detectability* requirement on the reader, not a write-time prevention — unchanged from the original decision, since no single-row `CHECK` constraint can see across rows to catch this. A direct self-cycle (`item_id = blocked_on_id`) *is* rejected at write time via a `CHECK` constraint on the edges table (see `data-model.md`) — this narrows, rather than changes, the original decision's own text ("a direct self-cycle is rejected at write time... longer cycles remain a detectability requirement on the reader"). For the reader-side detectability requirement, SQLite's recursive common table expressions (`WITH RECURSIVE`) let reconciliation walk the `blocked_by` graph and report `cycle_detected` as a single query — see `data-model.md` — rather than requiring bespoke graph-traversal code or a dependency/DAG library (still explicitly out of scope, unchanged).

**Alternatives considered**:
- *Mutate B's `blocked_by` to remove A the moment A completes*: rejected, unchanged from the original decision's reasoning — this destroys the historical fact "B was declared to depend on A" for no benefit the retained, thinned row doesn't already provide more cheaply, and reintroduces a reverse-index-scan-and-rewrite operation this design has no need for.
- *A separate `tombstones` table with its own two-step resolution* (the direct SQL mirror of the file-based design): rejected — see "Decision: retention" above; this is exactly the mechanical translation this correction's brief asks not to default to, and it would forfeit the single-table-lookup simplification for no benefit.
- *A dependency/DAG library or bespoke cycle-detection module*: rejected, unchanged from the original decision and from `plans/active/2026-08-24-symphony-coordination-exploration.md`'s own explicit rejection of dependency/DAG modeling — a recursive CTE is a query, not a solver; it computes no ordering, priority, or schedule, only reachability.

## Decision: claim atomicity — a database constraint replaces exclusive file creation

**Problem** (unchanged framing, restated for the new mechanism): a claim's *acquisition* must be decided by a single, atomic, exclusive operation — never a read-then-decide-then-write sequence — so that of any number of concurrent claim attempts against the same work item, exactly one succeeds and every other attempt receives an immediate, unambiguous failure (FR-018, SC-004a).

**Decision**: A work item's claim lives as (at most) one row in a dedicated `work_item_claims` table, keyed by `work_item_id` as its `PRIMARY KEY`. Acquiring a claim is a single `INSERT INTO work_item_claims (work_item_id, owner, claimed_at, worktree_path, branch) VALUES (?, ?, ?, ?, ?)`. If a row for that `work_item_id` already exists, SQLite rejects the insert with a primary-key constraint violation — an immediate, deterministic failure, never a timeout or an ambiguous result. See `data-model.md`'s "Claims" section for the full field-level contract.

**This decision supersedes the mechanism, not the guarantee, of the original "Decision: claim atomicity."** The original decision's *guarantee* — existence of a claim record, not its content, decides ownership; exactly one concurrent acquire attempt succeeds; every other attempt fails immediately and unambiguously — is unchanged and is now provided by SQLite's own primary-key constraint enforcement and single-writer transaction serialization, in place of `open(..., O_CREAT | O_EXCL)` against a dedicated file path. The original decision explicitly noted that this same class of guarantee is "available to plain files exactly as it would be needed underneath a SQLite `INSERT ... WHERE NOT EXISTS` or a unique-constraint insert" — that observation was correct, and is exactly why this override does not need to re-derive the atomicity argument from scratch: the primitive was always going to be "an exclusive, all-or-nothing create," and SQLite's constraint enforcement is that same primitive, now provided by the database engine directly rather than assembled from a filesystem syscall plus a dedicated file per claimed item.

**A genuine behavioral improvement, not merely a representation change, in the crash case.** The original decision's crash scenario — a process crashes after creating the claim file but before writing `owner`/`claimed_at` into it, leaving an empty or unparsable file that must be surfaced as a distinct `corrupt_claim` finding rather than trusted or treated as available — is **structurally prevented** by SQLite's transactional atomicity for the ordinary case: a single `INSERT` statement either commits in full (row exists with every `NOT NULL` column populated) or is rolled back entirely (row does not exist at all) if the process crashes before commit. There is no reachable intermediate state, via an ordinary application crash, in which a claim row exists but is missing its content — see the final report accompanying this revision for the corresponding change to spec.md's SC-010 and Edge Cases wording, and `data-model.md`'s "Claims" section for exactly what now still legitimately produces a `corrupt_claim` finding (database-file-level corruption, or a connection that ran with constraints disabled — a narrower, rarer trigger than the original decision described, not a removed concept).

**Why a dedicated claims table rather than a nullable `claim_owner` column on `work_items` itself**: this mirrors the original decision's own "why a separate file rather than an in-place, revision-checked update" reasoning, translated directly — a claim column on the same row as `title`/`status`/`blocked_by` would make acquiring a claim an `UPDATE ... WHERE claim_owner IS NULL` compare-and-swap, which still works correctly under SQLite's transaction isolation, but a dedicated table with its own primary key is simpler to reason about (existence *is* the claim, exactly as before) and avoids coupling claim churn to the same row every other mutation (status, evidence, dependency edges) touches, keeping the "claiming never has to read or reason about the rest of the item's fields" property the original decision valued.

**Release**: unchanged in shape from the original decision — `DELETE FROM work_item_claims WHERE work_item_id = ?` is a single, atomic, idempotent-if-absent operation. An ordinary release (by the recorded owner) is unconditional; a release by anyone else remains an override, permitted only on the basis of an observed `stale_claim` or `corrupt_claim` reconciliation finding — a documented process expectation the schema does not, and is not asked to, cryptographically enforce, unchanged from the original decision's own "consistent with this repository's existing single-operator trust model."

**Alternatives considered**: everything the original decision considered and rejected (a two-file "lock, then commit" pattern; a per-repository mutex covering all claims) is rejected again here for the same reasons, now translated to "a two-phase INSERT-then-UPDATE pattern" and "a single global advisory lock/transaction serializing all claims respectively" — both add ceremony a single-statement, constraint-enforced `INSERT` already resolves without needing any additional machinery.

## Decision: claim safety — reconciliation is read-only and never silently mutates

**Decision**: Reconciliation (comparing a claim row's recorded `worktree_path`/`branch` against actual repository state) is a read-only report; it never auto-releases, auto-completes, or auto-mutates a work item's or claim's stored facts — including when it finds a claim stale or corrupt. Staleness/corruption does not change what "Available to start" computes for that item either (`data-model.md`); the item remains claimed, by design, until someone performs the explicit override release. This decision is unchanged in substance from the original — only "Claim Record"/file language becomes "claim row"/database language throughout.

**Rationale**: Matches this repository's existing "no silent promotion" posture (D016's observed→candidate→current lifecycle requires an explicit act) and `docs/DATA-OWNERSHIP.md`'s trust-boundary language for projectmem ("treat its contents as leads, not conclusions"). It also matches the guardrail precedent that any future *mutating* Bindle command "must support preview before apply" (`AGENTS.md`, "Runtime isolation"). A stale or corrupt claim is surfaced for a human or agent to resolve, exactly like `bindle status`/`bindle skills status` surface `conflict` states today (D035) rather than auto-repairing them. This decision deliberately introduces **no** lease, heartbeat, timeout, or daemon: "explicit recovery" means the override can happen the instant staleness is noticed, by the same read-then-delete operation any release already uses (now a `DELETE` statement rather than a filesystem unlink) — the fix for "stranding" is that a recovery operation exists and is cheap to invoke on demand, not that anything expires automatically. Reconciliation itself never opens a write transaction against the ledger — every check it performs is a `SELECT` plus filesystem/Git observation.

## Decision: schema versioning and migration ownership

**Decision**: Schema version is tracked using SQLite's own built-in `PRAGMA user_version` (an integer stored in the database file's header, not a table) rather than a bespoke migrations table or an external migration framework. On opening the database, Bindle's own code checks `user_version`: `0` means an uninitialized file, so the schema in `data-model.md` is created and `user_version` is set to `1`; a nonzero value is compared against the schema version Bindle's own code currently expects, and a future schema change bumps the constant and adds one small, explicit migration step keyed by the version number it moves *from*.

**Rationale**: `PRAGMA user_version` is a SQLite-native, zero-dependency mechanism — no ORM, no third-party migration library (Alembic or similar), and no bespoke `schema_migrations` table are introduced, consistent with this decision's own "deliberately small and boring" brief and with this repository's existing "prefer the smallest model" posture. At this ledger's scale (a handful to a few dozen work items, a small number of tables), a linear sequence of small, explicit migration steps is sufficient; nothing here anticipates branching schema history, rollback tooling, or concurrent-schema-version support, none of which this feature has any evidence of needing.

**Alternatives considered**: A `schema_migrations` table recording applied migration names (the common web-framework pattern): rejected as unnecessary machinery at this scale — `PRAGMA user_version` gives the same "what version is this file at" fact without an extra table to create, query, and keep in sync with the migration code itself. A third-party migration framework: rejected outright, consistent with "no ORM... without an independently demonstrated need."

## Decision: connection lifecycle and concurrency for multiple local agent processes

**Decision**: Bindle's own code opens a short-lived connection per operation (or per command invocation), performs its reads/writes — wrapping any multi-statement mutation in an explicit transaction (see "Decision: transaction boundaries" below) — and closes the connection; no long-lived connection or daemon process holds the database open between invocations, consistent with `AGENTS.md`'s "On when in use" posture (no always-on processes). Every connection, on open, sets:

- `PRAGMA foreign_keys = ON` — **mandatory**, since SQLite disables foreign-key enforcement by default per connection; this is the setting that makes the dependency-integrity guarantee in "Decision: dependency resolution across archival" hold in the normal write path. A connection that omits this setting is an operational mistake, not a supported configuration.
- `PRAGMA journal_mode = WAL` — write-ahead logging, so concurrent readers are not blocked by an in-progress writer, appropriate for "one or more concurrently active agents/sessions" (plan.md's Technical Context, unchanged) each opening their own short-lived connection. WAL mode is persisted in the database file itself after first being set, but is re-stated on every connection open for clarity and because a fresh/copied database file may not have it set yet.
- `PRAGMA busy_timeout = <a small bound, e.g. 2000ms>` — so a writer that finds the database's single write-lock briefly held by another local process waits briefly and retries rather than failing immediately with `SQLITE_BUSY`. This governs *lock acquisition*, not the semantic outcome of a claim attempt: once a writer's `INSERT`/`UPDATE`/`DELETE` actually executes, the constraint or `WHERE`-guard outcome is immediate and deterministic, exactly as described above — `busy_timeout` only affects how long a caller may wait to get the chance to attempt its statement at all.

**Concurrency assumptions**: SQLite serializes writers at the whole-database level (WAL mode allows concurrent *readers* alongside one writer, but still only one writer at a time) — there is no per-table or per-row lock the way a client-server RDBMS offers. At this feature's stated scale (a handful to a few dozen work items; occasional local agent processes, not a fleet), this is not a bottleneck: every write transaction this design defines is a single short statement or a small, fixed handful of statements (see "Decision: transaction boundaries" below), so lock hold time per writer is on the order of milliseconds, not a shared resource multiple agents meaningfully contend over. This mirrors the original plan's own "Performance Goals: N/A at this scale" framing — nothing here changes that assessment, and nothing here introduces connection pooling, read replicas, or any concurrency machinery beyond what SQLite already provides out of the box.

**Alternatives considered**: A single long-lived daemon process owning the only connection, with other processes talking to it over a socket or pipe: rejected outright — this is exactly the daemon `AGENTS.md`'s "On when in use" and this repository's own "no always-on daemons" posture (per project memory) forbid, and nothing about this feature's scale or concurrency needs justifies introducing one. SQLite's own default `DELETE` journal mode (no WAL): rejected in favor of WAL specifically because rollback-journal mode serializes *readers* behind an in-progress writer too, which is a worse fit for "multiple agents each reading availability while another agent claims something," a normal expected access pattern here.

## Decision: transaction boundaries for multi-fact mutations

**Decision**: every mutation that changes more than one related, durable fact runs inside one explicit `BEGIN IMMEDIATE` … `COMMIT` transaction, so a crash or interruption mid-mutation leaves the ledger in exactly the state it was in before the mutation started — never a partially-applied intermediate state. `BEGIN IMMEDIATE` (rather than a deferred/implicit transaction) is used for any transaction that will write, so lock acquisition fails fast on contention rather than risking a mid-transaction upgrade failure. The mutations this applies to, and their statement-level boundary:

| Mutation | Statements inside one transaction |
|---|---|
| Create a work item, optionally with initial `blocked_by` edges | One `INSERT` into `work_items`, plus one `INSERT` per declared edge into `work_item_blocked_by` — all-or-nothing, so an item is never recorded with only some of its declared dependencies. |
| Add an evidence pointer | Single `INSERT` into `work_item_evidence` — atomic by itself; no explicit transaction required beyond SQLite's own single-statement atomicity. |
| Transition to `done` | Single `UPDATE work_items SET status = 'done', updated_at = ? WHERE id = ? AND status = 'open'`, checking the affected-row count is exactly one — the `WHERE status = 'open'` guard prevents a double-transition race the same way a claim's primary key prevents a double-claim race, without needing a separate transaction. |
| Transition to `superseded` | Single `UPDATE work_items SET status = 'superseded', superseded_by = ?, updated_at = ? WHERE id = ? AND status = 'open'` — the paired-columns invariant (`superseded_by` set if and only if `status = 'superseded'`) is additionally enforced by the table's own `CHECK` constraint, so this statement cannot leave the pairing inconsistent even without the transaction. |
| **Archive** (thin a terminal item in place) | One transaction: (1) `UPDATE work_items` clearing `title`/`source_kind`/`source_locator`/`source_promoted_by`/`created_at` and setting `archived_at`/`updated_at`, `WHERE id = ? AND status IN ('done', 'superseded')`; (2) `DELETE FROM work_item_evidence WHERE work_item_id = ?`; (3) `DELETE FROM work_item_blocked_by WHERE work_item_id = ?` (edges this item declared, never edges other items declare against it); (4) `DELETE FROM work_item_claims WHERE work_item_id = ?` (defensive — archival is only expected to run once no claim remains, but this guarantees no orphaned claim row can survive it). This is the direct database-transaction replacement for the original decision's informal "archiving and tombstoning happen together, never two separately-timed steps" guarantee — now a literal ACID property instead of a design intention. |
| Claim acquire | Single `INSERT` into `work_item_claims` — atomic by itself (see "Decision: claim atomicity"). |
| Claim release (ordinary) | Single `DELETE FROM work_item_claims WHERE work_item_id = ? AND owner = ?` — atomic by itself. |
| Claim release (override) with an optional Evidence Pointer noting the justification | One transaction: `DELETE FROM work_item_claims WHERE work_item_id = ?`, plus `INSERT INTO work_item_evidence (...)` with `kind = 'other'` — so the release and its optional justification note are recorded together or not at all, when the caller chooses to record one (still optional, unchanged from the original decision). |

**Rationale**: this directly answers the correction's own instruction to "explicitly establish the transaction boundary for mutations that change multiple related facts" and "a logical ledger action should not expose partially applied durable state when SQLite can make the action atomic." Every multi-statement row above previously required either an informal cross-artifact atomicity argument (archival/tombstoning) or was not previously represented as a single logical action at all (a guarded status transition, a release-with-justification-note) — SQLite transactions make each of these a literal, testable ACID property rather than a documented intention.

## Decision: corruption, recovery, and inspectability

**Decision**: `PRAGMA integrity_check` is the supported way to detect database-file-level corruption (distinct from an application-level `corrupt_claim` finding, which concerns a specific row, not the whole file); recovery from genuine file-level corruption is "restore from a backup, or regenerate work items by re-promoting from their upstream Spec Kit/plan source" — the same posture the original decision already held for undetectable claim-owner abandonment ("a human applying judgment... remains the only recourse"), now extended to file-level corruption. No automatic repair, replication, or backup service is introduced — consistent with "no hosted service or control plane" and this repository's "no always-on daemons" posture. `PRAGMA journal_mode = WAL` together with `PRAGMA synchronous = NORMAL` is the recommended durability setting: committed transactions survive an application crash or process kill (the ordinary case this ledger's crash scenarios above are about), at a well-established, standard tradeoff against the stronger (and slower) `synchronous = FULL` guarantee against power loss/OS crash mid-write — an appropriate level for local developer tooling, not a hosted service with uptime guarantees, and not a case this feature's scale or stated constraints call for over-engineering past.

**Direct SQL inspectability is an explicitly supported operational property**, not an incidental one: `sqlite3 <path-to-ledger> "SELECT ..."`, or any general-purpose SQLite GUI/CLI tool, can query the ledger ad hoc without going through Bindle's own code at all — this was one of the two headline reasons for this persistence-model correction (see "Decision: storage format" above) and is recorded here as a settled property future implementation and documentation should preserve, not incidentally break (e.g., by encrypting the file, or by using a schema-in-application-memory-only pattern that does not reflect true column names into the file).

**Rationale**: matches `docs/SCOPE.md`'s "simple inspection/recovery" storage criterion, applied to the new format rather than dropped by it — the original decision's inspectability argument favored plain text specifically because SQLite's own inspection story was judged (at that time) to need "the `sqlite3` CLI or matching schema knowledge." That CLI is a standard, near-universally available tool (and the schema is now documented directly in `data-model.md`), so this correction judges that bar as already met, not lowered.

**Alternatives considered**: An application-level checksum or integrity marker layered on top of SQLite's own file format: rejected — `PRAGMA integrity_check` already provides this, using the database engine's own well-tested internal consistency checks rather than a bespoke Bindle-owned one. Automatic backup-on-write or a replication mechanism: rejected outright as introducing exactly the kind of hosted-service/control-plane machinery this feature's constraints forbid, and unjustified at this feature's stated scale.

## Decision: projection contract with Symphony — resolved from the pinned fork's actual source, not the stale exploration plan

**Finding** (this session, the operator's local checkout of the pinned Symphony fork at commit `099535b`, matching `docs/SYMPHONY.md`'s pin):

- The `Tracker` behaviour (`elixir/lib/symphony_elixir/tracker.ex:23-32`) requires only read callbacks (`fetch_issues_by_states/1`, `fetch_issues_by_ids/1`, `secret_environment_names/1`); there is **no write/claim callback** — Symphony's orchestrator holds claims itself, entirely in-memory (`orchestrator.ex`, `state.claimed` `MapSet`), never persisted to the tracker.

- **`dispatchable` is hardcoded `true` by the `local` adapter** (`local/adapter.ex:90`) — it does **not** compute eligibility from `blocked_by` at all, even though `blocked_by` is present in the schema. Upstream `SPEC.md` (§11.3, lines 1259–1284) normatively requires `dispatchable` to be adapter-computed and explicit, and separately states `blocked_by` is "best-effort metadata; adapters MUST NOT invent blocker semantics they cannot represent reliably" — the `local` adapter's authors chose not to implement blocker semantics, which is allowed, not a bug.
- `active_states`/`terminal_states` are confirmed arbitrary, WORKFLOW.md-configured strings with pure set-membership semantics (`orchestrator.ex:883-908`) — no state names are hardcoded.
- Dispatch order is `{priority_rank(priority), created_at, identifier}` (`orchestrator.ex:803-814`); `priority` is a plain integer field, unranked/`nil` values sort last.
- `branch_name`/`url` are read into the `Issue` struct but **never dereferenced for workspace routing** — `branch_name` has zero other call sites in `lib/`; `url` is display-only (dashboard links).

**Decision**: This has a direct, load-bearing consequence for the projection contract: because the `local` adapter never gates on `blocked_by`, **Bindle's projection step, not Symphony, must resolve blocking before generating the projection** — a blocked item must simply not appear in an `active_state` in the generated `local_tracker.json` (or must be omitted/held in a distinct non-active state) until its blockers clear. This is not Bindle building a scheduler; it is satisfying the same adapter-computed-eligibility contract `SPEC.md` §11.3 places on every tracker adapter, done at projection-generation time rather than by writing a new, richer tracker adapter. This also means "not active" is not itself a safe target on its own: `plans/active/2026-08-24-symphony-coordination-exploration.md`'s Evidence section records that `active_states`/`terminal_states` are two independently-configured membership sets with no implicit third "withheld" status — a state string that is not a member of `active_states` is only correctly non-runnable if it is also not a member of `terminal_states` (see `contracts/coordinator-projection.md` for the resulting constraint on the projection's state assignment, not just its eligibility fact). See `contracts/coordinator-projection.md` for the precise field mapping.

This decision, and the finding it rests on, are entirely independent of Bindle's own persistence mechanism: Symphony's tracker-adapter contract does not know or care whether the projection was generated by reading a directory of TOML files or by querying a SQLite database — both this persistence-model correction and the original decision leave this section unchanged, apart from this note.

**Alternatives considered**: Writing a custom Symphony tracker adapter that reads Bindle's ledger directly and computes `dispatchable` itself from `blocked_by` (rejected for this plan — that is exactly the "Symphony adapter implementation" this feature's own brief puts out of scope; it remains a legitimate future option once the projection-file approach is validated, without changing the ledger's own model). Note also that Symphony's own possible future `sqlite` tracker adapter (`plans/active/2026-08-24-symphony-coordination-exploration.md`'s "Settled direction" section, itself already flagged there as inaccurate to what the pinned fork actually shipped — see that plan's own "Evidence" section) is a wholly separate SQLite usage from this ledger's own database, should Symphony ever gain one: one would be Symphony's own tracker storage, reached through Symphony's tracker-adapter seam; this one is Bindle's own durable ledger, reached only through Bindle's own code. The two are not the same database and this decision does not conflate them.
