# Phase 0 Research: Durable Work Ledger

Every decision below is grounded in repository evidence gathered and cited directly — `AGENTS.md`, `docs/PHILOSOPHY.md`, `docs/SCOPE.md`, `docs/DATA-OWNERSHIP.md`, `docs/DECISIONS.md` (D014–D016, D033, D035, D036, D037), `docs/WORKTREES.md`, `plans/active/2026-08-24-symphony-coordination-exploration.md`, `docs/SYMPHONY.md`, `src/bindle/repo.py`, and the pinned Symphony fork's own Elixir source at commit `099535b` (the operator's local checkout of the fork named in `docs/SYMPHONY.md`, verified this session to be checked out at exactly that pin). No NEEDS CLARIFICATION markers remain — none of the Technical Context slots required a real clarification decision from the user; each is resolved from existing repository evidence below.

## Decision: ownership — who owns the durable coordination facts?

**Decision**: Bindle owns the ledger's format and store, as a new, explicitly bounded kind of Bindle-owned state — **coordination state for currently/recently pending decomposed work** — distinct from the "user history" `docs/PHILOSOPHY.md` forbids Bindle from owning, and distinct from "working reasoning" (projectmem's own domain).

**Rationale**: The three-question admission screen (`AGENTS.md`, "Architecture rules"; `docs/PHILOSOPHY.md`, "Feature admission test") was applied to every plausible alternative owner before concluding this:

- **Git alone**: rejected by the task's own explicit constraint and by evidence — commits/branches encode *what happened*, not *what is currently blocked, claimed, or available*. `docs/WORKTREES.md`'s own "History scenarios" table treats branch/commit facts as historical observations, not live coordination state; nothing in Git represents "item X is currently claimed by agent Y."
- **GitHub Issues/PRs**: rejected — `AGENTS.md` ("Planning") explicitly states "Do not require GitHub Issues," and this ledger must work fully offline and across worktrees without a network round-trip (`docs/SCOPE.md`'s "Bindle does not own... GitHub issue tracking"). GitHub remains a valid *evidence pointer* target (a PR number an item can reference), never the required substrate.
- **Projectmem**: rejected as the *owner*, not merely deprioritized — projectmem's own domain is append-only working reasoning (issues/attempts/fixes/decisions) about *why* something happened, and it is explicitly branch-blind (`docs/DATA-OWNERSHIP.md`, "Trust boundary" note: "events carry only a HEAD SHA — no branch, no worktree, no rewrite handling"). The ledger's job is close to the opposite: current, mutable, worktree/branch-aware coordination facts (claimed-by-whom-in-which-worktree, blocked-on-what) that must stay accurate as of *now*, not an append-only log of *what an agent believed happened*. `docs/PHILOSOPHY.md`'s own rejection example ("Re-implement repository memory because projectmem is branch-blind... an imperfect integration does not justify duplication") does not apply here, because this is not a re-implementation of projectmem's own domain — it is a different domain projectmem was never designed to hold.
- **Symphony's own tracker** (`.symphony/local_tracker.json`, confirmed this session at the pinned fork revision): rejected as the *source of truth*, though it is exactly right as the *target of a generated projection*. Symphony's own `Tracker` behaviour (`elixir/lib/symphony_elixir/tracker.ex`) has no write/claim/update callback beyond `set_issue_state/3`, no `dispatchable` field for the `local` adapter (hardcoded `true` — see "Decision: projection contract" below), and its shape is Symphony's own adapter concern, swappable for Linear/GitHub/Jira/Asana/GitLab per Symphony's own `SPEC.md`. Coupling Bindle's durable model 1:1 to one adapter's JSON shape would violate D014 (replaceability) the moment Symphony is replaced or a different tracker adapter is selected, and would let an external tool's format decide Bindle's own ontology — exactly what the task's own brief forbids ("Symphony does not become the authoritative ontology for Bindle's work").
- **A new Bindle-owned store**: the only remaining candidate, and the one the task's own framing anticipates ("Determine what the durable implementation-work record actually is... Who naturally owns it?"). This passes `docs/PHILOSOPHY.md`'s nine-criteria test: it bridges intent (Spec Kit/plans) and execution (a future coordinator) — a real, previously-unbridged seam (criterion 1); it operates through Bindle's own supported read/write functions on its own files, no other tool's private store (criterion 2); its output *toward* a coordinator is a disposable, regenerable projection (criterion 3); it does not become the sole owner of user history (criterion 4 — see below); it stays useful if Symphony is replaced by a different coordinator, since the projection step is the only coordinator-specific part (criterion 5); it solves an observed, named repeated need (surviving session/context loss across concurrent agent work), not hypothetical scope (criterion 6); it cannot be handled by a routing rule or small script alone — the underlying facts (claim, blocking) do not yet exist anywhere to route (criterion 7); it is explicitly designed around the Git-common-directory identity model (criterion 8, `docs/WORKTREES.md`); and it does not preserve completed items forever merely because preservation is possible — see "Decision: retention" below (criterion 9).

**Philosophy-and-scope implication, stated plainly rather than routed around**: `docs/PHILOSOPHY.md`'s current "Bindle-owned runtime state" language ("configuration, disposable cache, and explicit export") and `docs/DATA-OWNERSHIP.md`'s ownership table do not yet have a row for this shape of state. This is not a request to relax D014–D016; it is a request to **add** an explicit, narrow acknowledgment that bounded, non-derivable, working *coordination* state (parallel to projectmem's own "working notes — not truth" bucket, but Bindel-owned because no adoptable third party covers this domain) is a distinct, admissible fourth category, provided it stays: (a) bounded to currently/recently pending work, never a permanent log; (b) never the only record of *why* work exists (that stays with Spec Kit/plans, FR-002/FR-017); and (c) never the only record of *that* work happened once it completes (that promotes to `docs/DECISIONS.md`/`plans/`/Git, same as today). This is a recommendation for a future `docs/DECISIONS.md` entry to make explicitly at adoption time, not a change this specification-only feature makes unilaterally.

**Alternatives considered**: A generic Bindle "Component/Provider" abstraction spanning guardrails/projectmem/skills/QMD/ledger — rejected outright per D033's and D035's own closing precedent ("two kits were enough to reveal real structural differences... a third, differently-shaped kit is the point at which to revisit," never triggered since each seam so far has stayed genuinely different-shaped).

## Decision: storage location — where does the ledger live?

**Decision**: The ledger's directory is resolved from the repository's Git common directory (`RepoInfo.repo_root`/`git_common_dir` in `src/bindle/repo.py`), **not** the invoking worktree root — e.g., conceptually `<repo_root>/.bindle-work/` (final path/name is an implementation-slice detail, not fixed by this plan).

**Rationale**: This exactly mirrors the correction D033 already made for Projectmem's own hook installation (`cwd=repo_root`, not `worktree_root`, because a linked worktree's `.git` is a *file*, not a directory) and matches `docs/WORKTREES.md`'s repository-identity rule directly: "The Git common directory is a local repository identity shared by linked worktrees." A ledger scoped to `git_common_dir` is visible and consistent from every linked worktree on this machine without any synchronization step, satisfying spec.md's FR-011 and User Story 3 (two worktrees, two claims, no interference) by construction — two worktrees resolve the same physical directory.

**Alternatives considered**:
- *Worktree-local storage* (like the skill kits' Codex materialization, D035): rejected — explicitly ruled out by the task's own brief ("Do not assume worktree-local state is sufficient... Work items should remain intelligible if a worktree disappears"), and it would mean two worktrees literally cannot see each other's claims, defeating User Story 3 outright.
- *Tracked, git-committed files following the checked-out branch* (like `bindle.toml`, `specs/`): considered seriously, then rejected for the ledger's *in-flight* coordination facts specifically. A tracked-per-branch file only becomes visible to another worktree once its owning branch is merged — meaning "is item X currently claimed" would silently depend on which branch happens to be checked out where, an inconsistency the spec's User Story 2/3 explicitly test against. It would also turn ordinary claim/status churn into commit noise on feature branches, and turn merges into a source of ledger-file conflicts unrelated to the actual code change. This is the same shape of problem Projectmem (D022) and QMD (D036) already solved by choosing repository-scoped, untracked, machine-local storage instead of tracking their own state — this plan follows that now twice-established precedent rather than inventing a third pattern. (See "Decision: retention" below for how a completed item still becomes durable, tracked history when that is actually wanted.)

## Decision: storage format — plain files, not SQLite

**Decision**: One plain-text file per work item (TOML, matching `bindle.toml`'s own precedent and this project's existing stdlib-only `tomllib` reading pattern from `src/bindle/skills/config.py`), not a single SQLite database.

**Rationale**, evaluated directly against `docs/SCOPE.md`'s and `docs/PHILOSOPHY.md`'s own stated requirements for Bindle-owned state:

- **Dependency weight is a non-argument either way.** `sqlite3` is Python stdlib, exactly like `tomllib` — this decision is not "avoid a dependency," it is about format properties.
- **Scale does not justify a database.** This ledger targets a handful to a few dozen concurrently-relevant items per repository (spec.md's own Assumptions: "does not... imply a scale ceiling," but every acceptance scenario is sized in single digits). At this scale, `rg`/directory listing/stdlib parsing are sufficient, mirroring this repository's own governing precedent for *not* reaching for heavier tooling before demonstrated need (`AGENTS.md`, "Code intelligence": "prefer... rg, fd, Git, and language tooling" before an adopted heavier tool; D020/D021's evaluate-before-adopt bar).
- **Inspectability and recovery.** `docs/SCOPE.md`'s own storage criteria list "simple inspection/recovery" and "no hidden irreplaceable history owned only by Bindle" as explicit tests. A directory of small text files can be read, diffed, hand-edited, and recovered with `cat`/a text editor even if `bindle` itself is broken or absent; a SQLite file cannot, without the `sqlite3` CLI or matching schema knowledge — a materially higher recovery bar for content this plan wants to keep genuinely inspectable.
- **One file per item, not one file for all items.** Rejected the alternative of a single JSON/TOML document holding every item (the shape Symphony's own `local_tracker.json` uses, and the shape the prior `feat/local-orchestration` branch's SQLite table effectively serialized to a single database file). A single shared file means every concurrent writer — even to unrelated items — contends on the same file, the opposite of spec.md's SC-004 ("two concurrently claimed, independent work items can each be updated... without either update overwriting... the other item's record"). Independent files give independent items true write independence, using the filesystem's own existing atomicity primitives (e.g., write-to-temp-then-rename) rather than requiring a transaction manager.
- **A directory of files still has directory-level races**, but they are cheap and standard to guard (an item-creation race is a create-if-absent check on one small file, not a schema migration or a locked table) — no `sqlite3` transaction semantics are needed, because deliberately, per spec.md's own Assumptions, this plan does not attempt sub-second in-process claim arbitration.
- **External precedent, not proof but corroborating signal**: Symphony's own shipped local tracker (`local/init.ex`, `local/store.ex`, confirmed this session at the pinned fork revision) chose a plain JSON file over SQLite for its own, structurally similar problem (a small number of tracked issues, one process, simple inspection). D037 already recorded this correction to the exploration plan's earlier, unverified SQLite assumption. This plan's own conclusion is independently derived from this repository's storage criteria, not copied from Symphony's choice — but the fact that a comparable system converged on the same answer is worth recording as corroboration.

**Alternatives considered**: SQLite (rejected, above); a single JSON Lines append log (rejected — an append-only log fits an event history, not current mutable state per item, and would need periodic compaction to answer "what is item X's current status" without replaying the whole log); a single YAML/JSON document with one entry per item, à la `local_tracker.json` (rejected for the write-independence reason above).

## Decision: retention — completed work leaves a tombstone, not a full historical copy

**Decision**: A work item reaching `done` or `superseded` is **archived out of the active ledger once reconciled**, and archiving it **atomically creates a permanent Tombstone** (`id`, terminal `status`, `superseded_by` — three fields, see `data-model.md`) in the same operation. "Reconciled" here is Bindle's own reconciliation-against-repository-state (the Reconciliation Report's domain — claim, evidence, and blocking drift); it is never satisfied by, or waiting on, an external coordinator generating a projection. Completion is authoritative in the ledger the moment `status` changes, and archival proceeds on Bindle's own timing regardless of whether a coordinator ever observed the item's terminal state first (`contracts/coordinator-projection.md`, "What the projection explicitly does not do"). The original phrase used in the first draft of this decision — "archived out... not retained indefinitely" — was not precise enough on its own: it correctly ruled out an ever-growing full-detail log, but left open exactly what, if anything, survives archival for dependency resolution to use. This revision closes that gap explicitly rather than leaving a future session to notice the ambiguity.

**Rationale**: `docs/PHILOSOPHY.md`'s preservation rule (D016) and criterion 9 of the feature admission test ("does not preserve information merely because preservation is possible") still govern — the *full* record (title, source, evidence, claim history) is discarded at archival, exactly as originally decided; nothing about resolving the dependency-lifetime question below reopens that. What changes is narrower: a fixed-size, three-field Tombstone per archived item is kept forever, specifically because `docs/DECISIONS.md`'s D014/D015 boundary between "durable" and "derived" has no room for a *missing* record to mean two different things at once (see next decision) — a tombstone is the smallest fact that removes that ambiguity. A tombstone is not a historical narrative and does not grow after creation; it is closer in kind to `bindle.toml`'s own fixed-shape configuration than to a log. This plan still does not specify the exact archival mechanism or trigger timing (a future implementation-slice detail) — only the constraint that archiving and tombstoning are the same atomic step, never two separately-timed steps that could leave a gap between them.

## Decision: dependency resolution across archival — a missing reference must never be ambiguous

**Problem** (raised directly against the original data model): if B is `blocked_by` A, A becomes `done`, and A is later archived, evaluating B's blocked status a week later needs an authoritative answer. The original model computed "blocked" by looking up each `blocked_by` id's live `status` — correct while A still exists as an active item, but silent about what happens once A is gone. A missing reference could then mean either "A finished and was cleaned up" (fine) or "A was never a valid id, or its record was lost" (a real problem) — and nothing distinguished the two.

**Decision**: `blocked_by` is a **stable, declared set of dependency edges — historical, not a live "still open" list.** It is never pruned or rewritten when a referenced item resolves; the ledger does not reach into B's record to remove A once A finishes. What *is* fully derived, on every evaluation, is whether each entry currently blocks: resolve the id against (1) the active item set, then (2) the Tombstone set (see previous decision), and only if **neither** contains it, treat it as `dangling_blocker` — genuinely unresolvable, kept conservatively "still blocking," and surfaced for explicit correction. Because archival always leaves a Tombstone in the same step, a satisfied-then-archived dependency is *guaranteed* to still resolve via (2) — a missing reference can therefore only ever mean "dangling/corrupt," never "completed previously." The two cases the problem statement asked to keep apart are kept apart by construction, not by a runtime check that could be skipped.

This also directly answers "attempts to archive an item that is still needed to resolve dependency truth": there is no such case. Archival and tombstoning happen together, so there is never a window where an item is gone but not yet resolvable — no precondition/guard ("is anyone still blocked on me?") is needed before archiving, which keeps this the smaller of the two designs considered below.

**Case-by-case outcomes** (all computed, never stored):
- Dependency still open (an active item, `status = open`) → still blocking.
- Dependency satisfied (an active item or a Tombstone with `status = done`) → satisfied.
- Dependency superseded (an active item or a Tombstone with `status = superseded`) → satisfied — unchanged from the original rule; the named work will not appear under that identity, and re-pointing to a replacement, if the dependency still matters, is an explicit act.
- Referenced item missing from both the active set and the Tombstone set → `dangling_blocker`, treated as still blocking (conservative default — never silently promoted to satisfied) and surfaced by reconciliation.

**Alternatives considered**:
- *Mutate B's `blocked_by` to remove A the moment A completes* ("completion atomically removes satisfied dependency edges from dependents," one option this decision was asked to evaluate): rejected. It would require, at the moment any item completes, finding every other item that names it (a reverse-index scan) and rewriting each one's file — a multi-file operation with no natural single-transaction boundary, reintroducing exactly the kind of coordinated-write complexity the per-item-file design exists to avoid. It also destroys the historical fact "B was declared to depend on A" for no benefit the Tombstone design doesn't already provide more cheaply.
- *No tombstone; defer/refuse archival while any active item still references the id*: rejected as strictly worse than the chosen design — it requires the same reverse-index scan as above just to decide whether archiving is currently "safe," and it still doesn't resolve the case where a *new* item is written naming an already-archived id later; a permanent Tombstone answers both without any precondition check at all.
- *Full historical copy retained on archival* (i.e., don't shrink the record at all): rejected — this is exactly "prefer the smallest model that does not turn Bindle into a permanent task-history database" failing; nothing about dependency resolution needs more than `id`/`status`/`superseded_by`.

## Decision: claim atomicity — a naive read-modify-write cannot be allowed to arbitrate a claim

**Problem** (raised directly against the original data model): the first draft embedded `claim` as a field inside the same per-item TOML file as `title`/`status`/`blocked_by`/`evidence`. Claiming it meant read the file, check `claim` is absent, write the file back with `claim` set — a classic read-modify-write race: two concurrent readers can both observe "unclaimed" before either writes, and both then believe they succeeded.

**Decision**: split the claim out of the Work Item's own file into a separate **Claim Record**, one small file per claimed item, whose *creation* is the only operation that decides ownership — see `data-model.md`'s "Claim Record" section for the full field-level contract (acquire/release/crash/staleness). The key property: acquiring a claim becomes a single atomic **create-if-absent** operation against one dedicated path, never a read-then-decide-then-write sequence against a file that also holds other fields. Concretely, the required primitive is POSIX exclusive file creation semantics (create the path; if it already exists, fail — never overwrite, never merge) — content is written into the file immediately after creation succeeds, which is why the "exactly one claimant" guarantee comes entirely from the create step, not from anything written afterward (see the crash case in `data-model.md`).

**Why this does not require SQLite, and does not reopen the storage-format decision**: the atomicity this contract needs comes from a directory-entry-level filesystem operation (`open(..., O_CREAT | O_EXCL)` or the equivalent), which is available to plain files exactly as it would be needed *underneath* a SQLite `INSERT ... WHERE NOT EXISTS` or a unique-constraint insert — a database would still be relying on the same class of underlying guarantee, just mediated through an extra process (the SQLite library) and an extra file format neither this repository's storage criteria nor this problem's scale calls for (`research.md`'s original "Decision: storage format," unchanged). If anything, resolving this concern with a plain-file primitive rather than reaching for a database *reconfirms* that decision instead of undermining it: the concurrency requirement was never actually an argument for SQLite, and correctly identifying the exact primitive needed (exclusive create, not read-modify-write) shows the plain-file design was under-specified, not wrong.

**Why a separate file rather than an in-place, revision-checked (compare-and-swap) update to the same item file**: a CAS scheme (read a revision marker, write only if it is unchanged) was considered and rejected as needlessly more complex here. Implementing CAS correctly against a plain file still requires some exclusive, atomic "did anyone change this since I read it" check — there is no simpler way to get that against a single shared file than the same exclusive-creation primitive this decision already uses, so CAS would only add complexity (a revision field, a retry loop, and a race between reading the revision and creating the replacement) without removing the need for the underlying primitive. Giving claims their own file sidesteps needing CAS at all: claiming never has to read or reason about the rest of the item's fields.

**Alternatives considered**: a lock file distinct from the claim's own content, released after the claim content is durably written (a two-file "lock, then commit" pattern) — rejected as unnecessary ceremony; the crash-window this would close (an empty/unparsable Claim Record after a mid-write crash) is already handled correctly by treating that state as a distinct, surfaced `corrupt_claim` finding rather than as available or as a normal claim, so the extra file buys no additional correctness for this problem's stakes. A per-repository lock covering all claims (a single mutex file) — rejected as exactly the kind of shared-contention-on-unrelated-work this design exists to avoid (`research.md`'s original "one file per item, not one file for all items" reasoning applies identically here).

## Decision: claim safety — reconciliation is read-only and never silently mutates

**Decision**: Reconciliation (comparing a claim's recorded worktree/branch against actual repository state) is a read-only report; it never auto-releases, auto-completes, or auto-mutates a work item's or Claim Record's stored facts — including when it finds a claim stale or corrupt. Staleness/corruption does not change what "Available to start" computes for that item either (`data-model.md`); the item remains claimed, by design, until someone performs the explicit override release.

**Rationale**: Matches this repository's existing "no silent promotion" posture (D016's observed→candidate→current lifecycle requires an explicit act) and `docs/DATA-OWNERSHIP.md`'s trust-boundary language for projectmem ("treat its contents as leads, not conclusions"). It also matches the guardrail precedent that any future *mutating* Bindle command "must support preview before apply" (`AGENTS.md`, "Runtime isolation"). A stale or corrupt claim is surfaced for a human or agent to resolve, exactly like `bindle status`/`bindle skills status` surface `conflict` states today (D035) rather than auto-repairing them. This decision deliberately introduces **no** lease, heartbeat, timeout, or daemon: "explicit recovery" means the override can happen the instant staleness is noticed, by the same read-then-delete operation any release already uses — the fix for "stranding" is that a recovery operation exists and is cheap to invoke on demand, not that anything expires automatically.

## Decision: projection contract with Symphony — resolved from the pinned fork's actual source, not the stale exploration plan

**Finding** (this session, the operator's local checkout of the pinned Symphony fork at commit `099535b`, matching `docs/SYMPHONY.md`'s pin):

- The `Tracker` behaviour (`elixir/lib/symphony_elixir/tracker.ex:23-32`) requires only read callbacks (`fetch_issues_by_states/1`, `fetch_issues_by_ids/1`, `secret_environment_names/1`); there is **no write/claim callback** — Symphony's orchestrator holds claims itself, entirely in-memory (`orchestrator.ex`, `state.claimed` `MapSet`), never persisted to the tracker.
- The `local` adapter's on-disk schema (`.symphony/local_tracker.json`, `local/adapter.ex:76-94`) is `{identifier, title, description, priority, state, branch_name, url, assignee_id, labels, blocked_by, created_at, updated_at}`, of which only `state` is ever mutated post-creation.
- **`dispatchable` is hardcoded `true` by the `local` adapter** (`local/adapter.ex:90`) — it does **not** compute eligibility from `blocked_by` at all, even though `blocked_by` is present in the schema. Upstream `SPEC.md` (§11.3, lines 1259–1284) normatively requires `dispatchable` to be adapter-computed and explicit, and separately states `blocked_by` is "best-effort metadata; adapters MUST NOT invent blocker semantics they cannot represent reliably" — the `local` adapter's authors chose not to implement blocker semantics, which is allowed, not a bug.
- `active_states`/`terminal_states` are confirmed arbitrary, WORKFLOW.md-configured strings with pure set-membership semantics (`orchestrator.ex:883-908`) — no state names are hardcoded.
- Dispatch order is `{priority_rank(priority), created_at, identifier}` (`orchestrator.ex:803-814`); `priority` is a plain integer field, unranked/`nil` values sort last.
- `branch_name`/`url` are read into the `Issue` struct but **never dereferenced for workspace routing** — `branch_name` has zero other call sites in `lib/`; `url` is display-only (dashboard links).

**Decision**: This has a direct, load-bearing consequence for the projection contract: because the `local` adapter never gates on `blocked_by`, **Bindle's projection step, not Symphony, must resolve blocking before generating the projection** — a blocked item must simply not appear in an `active_state` in the generated `local_tracker.json` (or must be omitted/held in a distinct non-active state) until its blockers clear. This is not Bindle building a scheduler; it is satisfying the same adapter-computed-eligibility contract `SPEC.md` §11.3 places on every tracker adapter, done at projection-generation time rather than by writing a new, richer tracker adapter. This also means "not active" is not itself a safe target on its own: `plans/active/2026-08-24-symphony-coordination-exploration.md`'s Evidence section records that `active_states`/`terminal_states` are two independently-configured membership sets with no implicit third "withheld" status — a state string that is not a member of `active_states` is only correctly non-runnable if it is also not a member of `terminal_states` (see `contracts/coordinator-projection.md` for the resulting constraint on the projection's state assignment, not just its eligibility fact). See `contracts/coordinator-projection.md` for the precise field mapping.

**Alternatives considered**: Writing a custom Symphony tracker adapter that reads Bindle's ledger directly and computes `dispatchable` itself from `blocked_by` (rejected for this plan — that is exactly the "Symphony adapter implementation" this feature's own brief puts out of scope; it remains a legitimate future option once the projection-file approach is validated, without changing the ledger's own model).
